# Knowledge base

The hosted scanner publishes one article per check at `/knowledge-base/<slug>`, with an index at `/knowledge-base` and one page per section. Every page is also served as Markdown (append `.md`, or send `Accept: text/markdown`), the index is data at `/knowledge-base.json`, the MCP tool `explain_check` returns an article, and everything is listed in `/llms.txt` and `/sitemap.xml`, so people, search engines and agents can all read and cite it.

## Where the content lives

- `packages/catalog/knowledge/<CHECK-ID>.md` holds the authored article for each check. Every check in the catalog needs one; `pnpm --filter @agentic-readiness/catalog validate` fails otherwise.
- The page adds the rest from the catalog, so an article never repeats it: the check's weight and priority tier, the levels it gates, the checks it depends on, the fix (summary, snippet and the prompt for a coding agent) and the list of specifications.
- `packages/catalog/src/generated/knowledge.ts` is generated by the catalog build. Do not edit it.

## File format

```markdown
---
slug: search-and-assistant-crawlers-allowed
headline: Let the crawlers behind AI answers read your product pages
description: One or two sentences, 120 to 170 characters, used as the meta description.
keywords: four to eight comma-separated search phrases
---

## In short

## What this check looks at

## Why it matters for AI agents

## How the scanner decides

## How to fix it

### WordPress and WooCommerce

### Shopify

### Any other stack

## Verify it yourself

## Common mistakes

## FAQ

### A question a store owner or developer would actually type?
```

All nine `##` sections are required, in this order. Under "How to fix it" use the three platform subsections when they apply; a check that only concerns one platform uses the subsections that make sense. The FAQ has three to five `###` questions, each ending with a question mark and answered in one short paragraph; they become FAQPage structured data.

The slug is permanent once published: it is the URL. Keep it short, lowercase, kebab-case and keyword-bearing.

## Supported Markdown

The renderer accepts a deliberate subset, so every article renders the same everywhere:

- `##` and `###` headings, paragraphs, `-` bullet lists and `1.` numbered lists (no nesting)
- fenced code blocks with a language (`bash`, `robots`, `html`, `json`, `http`, `liquid`, `php`, `text`)
- `inline code`, `**bold**`, `[links](https://...)` and links to other articles as `/knowledge-base/<slug>`
- pipe tables with a header row

No raw HTML, no images, no nested lists, no headings below `###`.

## Writing rules

- **Answer first.** "In short" answers the question in two or three sentences that stand alone; agents and search snippets quote it.
- **Plain, short sentences.** One idea per sentence. No em dashes. Explain every acronym the first time.
- **Accurate before complete.** "How the scanner decides" must match the check's `method` in the catalog and its implementation in `packages/core/src/checks`. Vendor behaviour is stated only when the check's specifications or the vendor's own documentation say so.
- **Never overclaim.** A passing check does not mean an agent will buy; say what the check proves and what it does not.
- **Concrete fixes.** Name the settings screen, template, plugin type or header. Point to the platform's own mechanism before custom code.
- **Verifiable.** "Verify it yourself" gives a command or a free tool a reader can run against their own site.
- **Neutral and public.** Nothing about unreleased partner work, internal integration status, launch timing or commercial terms. No plugin is endorsed by name unless it is the platform's own or the common default, and then only as an example.
