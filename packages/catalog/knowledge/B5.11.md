## In short

A UCP (Universal Commerce Protocol, an open standard for agents to discover and buy from stores) profile can say that the store's shopping service speaks MCP (Model Context Protocol, through which AI agents call tools on a server). It can also say that the store offers a checkout or a cart. UCP names the MCP tools that go with each of these. This check asks the declared MCP server for its list of tools and compares it with what the profile promises. It does not gate a level and does not lift the commerce score's cap.

## What this check looks at

The profile at `/.well-known/ucp` holds two parts that matter here:

- **Services.** A `dev.ucp.shopping` entry with `"transport": "mcp"` and an `endpoint` says that agents can reach the shopping service over MCP at that URL.
- **Capabilities.** `dev.ucp.shopping.checkout` is the checkout capability and `dev.ucp.shopping.cart` is the cart capability.

```json
{
  "ucp": {
    "version": "2026-08-25",
    "services": {
      "dev.ucp.shopping": [
        { "version": "2026-08-25", "transport": "mcp", "endpoint": "https://example.com/ucp/mcp" }
      ]
    },
    "capabilities": {
      "dev.ucp.shopping.checkout": [{ "version": "2026-08-25" }],
      "dev.ucp.shopping.cart": [{ "version": "2026-08-25" }]
    },
    "payment_handlers": {}
  }
}
```

UCP's MCP bindings map each capability's operations to MCP tools with fixed names:

| Capability                  | MCP tools                                                                                    |
| --------------------------- | -------------------------------------------------------------------------------------------- |
| `dev.ucp.shopping.checkout` | `create_checkout`, `get_checkout`, `update_checkout`, `complete_checkout`, `cancel_checkout` |
| `dev.ucp.shopping.cart`     | `create_cart`, `get_cart`, `update_cart`, `cancel_cart`                                      |

The checkout binding's conformance section requires an implementation to provide all core checkout tools. An MCP client asks a server for its tools with the `tools/list` method and runs one with `tools/call`. This check uses only `tools/list`.

## Why it matters for AI agents

An agent that supports UCP reads the profile, sees a cart over MCP and calls `create_cart` on the endpoint. If the server has no such tool, the call fails, and the agent cannot buy even though the profile said it could. A profile that promises more than the server delivers is worse than a smaller, honest profile.

One gap shows up in real profiles: the profile declares the cart capability, but the MCP server lists no cart tools.

A pass shows that the server lists every tool the declared capabilities need. It does not show that the tools work, that they accept the right arguments or that a checkout completes. The scanner never calls a tool.

## How the scanner decides

The check uses the profile the [UCP profile check](/knowledge-base/ucp-business-profile) recorded. It runs when that check passed or warned, and is skipped when it failed or was skipped.

It goes on only when both of these hold:

- the `dev.ucp.shopping` service has an entry with the transport `mcp` and an endpoint
- the profile declares the checkout or the cart capability, or both, with at least one entry

The scanner then lists the server's tools with read-only JSON-RPC requests (JSON-RPC is a simple format for calling a method on a server with JSON), at most four in all:

1. It sends `tools/list` without a session, as the 2026-07-28 MCP transport allows, with the headers `MCP-Protocol-Version: 2026-07-28` and `Mcp-Method: tools/list`.
2. If the answer holds a tool list, it uses that list. If the answer is HTTP 401, with or without a `WWW-Authenticate` header, the server wants authorisation first, and the check is skipped.
3. Otherwise it falls back to the older 2025-06-18 transport: an `initialize` handshake, the `notifications/initialized` message and `tools/list` in the session the handshake opened.

The scanner reads answers in plain JSON and in server-sent-event framing. It then compares the tool names with the table above, for the declared capabilities only.

- **Pass:** every tool for each declared capability is listed. Extra tools are fine.
- **Warn:** some of the tools are missing, and the report names them. Also a warning: robots.txt disallows the endpoint for the scanner, so it did not ask.
- **Fail:** the server lists none of the tools for the declared capabilities, or it does not answer with a tool list at all.
- **Skip:** the profile declares no MCP binding for shopping or neither capability, the endpoint requires authorisation before it lists tools, or it cannot be reached.

Only the names are compared. The scanner does not check the tools' input schemas or behaviour.

## How to fix it

Make the profile and the server agree. Either add the missing tools or stop declaring the capability.

### Shopify

- Shopify generates the UCP profile for eligible stores and runs the services it declares. There is nothing to change in your theme.
- If this check reports missing tools on a profile Shopify serves, contact Shopify Support with the report.

### WordPress and WooCommerce

- WooCommerce has no built-in UCP support. A UCP extension or a payment provider's integration provides the profile and the MCP server. Update it first.
- If the profile still declares a capability the server does not support, look for a setting that turns the capability off, or report the gap to the extension's developer.

### Your own UCP implementation

- Implement each missing tool as UCP's checkout and cart MCP specifications describe it. Use the exact names from the table.
- Until a capability's tools exist, remove that capability from the profile.
- Make `tools/list` answer without a session, or support the `initialize` handshake. If the server demands authorisation before it lists tools, the scanner cannot compare and skips the check.
- Check that the endpoint in the profile is the production server, not a staging host.
- If robots.txt disallows the endpoint, agents that honour robots.txt will not call it. Allow the path explicitly.

## Verify it yourself

Find the MCP endpoint in the profile:

```bash
curl -s https://example.com/.well-known/ucp | jq -r '.ucp.services["dev.ucp.shopping"][] | select(.transport == "mcp") | .endpoint'
```

Ask that endpoint for its tools, without a session:

```bash
curl -s -X POST https://example.com/ucp/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: tools/list' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{
    "io.modelcontextprotocol/protocolVersion":"2026-07-28",
    "io.modelcontextprotocol/clientInfo":{"name":"curl","version":"1"},
    "io.modelcontextprotocol/clientCapabilities":{}}}}'
```

The `_meta` object carries what a session used to: the protocol version and who is asking. The scanner sends the same fields.

Look for each tool name in `result.tools`. If the answer starts with `event:` or `data:`, the JSON follows `data:`. If the server refuses a request without a session, send an `initialize` request first and repeat `tools/list` with the `Mcp-Session-Id` header it returns.

## Common mistakes

- **Cart declared, no cart tools.** The profile lists `dev.ucp.shopping.cart`, but the server offers only checkout tools.
- **Different tool names.** `createCheckout` or `checkout_create` is not `create_checkout`. Agents look for the exact names.
- **A partial checkout.** A server with `create_checkout` and `get_checkout` but no `complete_checkout` cannot finish a purchase.
- **An endpoint copied from staging.** The profile points at a host that does not answer in production.
- **A profile that runs ahead of the server.** A capability added to the profile before its tools are deployed.

## FAQ

### Does the scanner create a checkout or a cart on my server?

No. It only asks for the list of tools and never calls one. When the server needs the older `initialize` handshake, that opens a session, as it does for every client, but nothing else is created or changed.

### My server offers more tools than UCP defines. Is that a problem?

No. The check looks only for the UCP tools of the capabilities you declare. Extra tools do not affect the result.

### Do I need both the checkout and the cart tools?

Only for the capabilities you declare. A profile that declares checkout but not cart needs the 5 checkout tools and none of the cart tools.

### Why was the check skipped when my MCP server requires a login?

The server answered with HTTP 401 and asked for authorisation before it would list its tools. The scanner never signs in, so it cannot see the list and does not guess.
