## In short

robots.txt is the first file a crawler or AI agent reads on your site. It must answer HTTP 200 with a plain text body that parses under RFC 9309, the Robots Exclusion Protocol. A missing file is tolerated but leaves your intent unstated; a server error, a challenge page or an HTML page in its place can stop crawlers from reading anything at all.

## What this check looks at

The scanner requests `https://your-host/robots.txt` once, on the host that serves your store. It records the HTTP status, the content type, how many groups the file contains and which `Sitemap:` lines it declares.

A robots.txt file is a list of groups. Each group starts with one or more `User-agent` lines and continues with `Allow` and `Disallow` path rules. `Sitemap:` lines can appear anywhere and point crawlers at your sitemap. RFC 9309 defines this format and also defines what a crawler must do when the file cannot be read.

That second part is what this check is really about. RFC 9309 and Google's documentation treat the outcomes very differently:

| What the server answers | What a crawler does                                       |
| ----------------------- | --------------------------------------------------------- |
| 200 with rules          | Follows the rules                                         |
| 404 or another 4xx      | Treats the site as fully allowed                          |
| 5xx or no answer        | Treats the site as fully disallowed, at least for a while |
| 200 with an HTML page   | Finds no valid rules in it                                |

## Why it matters for AI agents

Every crawler that builds an index for AI answers reads robots.txt before anything else. So do many agents that fetch a page because a user asked them to. If the file answers with a server error, a well-behaved crawler has to assume it may not crawl. Google documents that it stops crawling a site whose robots.txt returns a 5xx error, and keeps using a cached copy or treats the site as disallowed for a period.

A challenge page is the same problem in disguise. A bot-protection service that answers robots.txt with a JavaScript challenge returns a 200 status with HTML. A crawler finds no rules in it, and the challenge itself tells you that automated clients are being stopped.

A missing file is much less serious. Crawlers then assume everything is allowed. The scanner still warns, because a store with no robots.txt cannot state a policy, cannot point crawlers at its sitemap, and cannot keep cart or account pages out of crawls.

This check carries weight 3, the blocking tier. It is a Level 1 gate, so a store that fails it cannot reach any level above 0. Every later robots.txt check, including [which crawlers may read product pages](/knowledge-base/search-and-assistant-crawlers-allowed), depends on this file being readable.

## How the scanner decides

- **Pass:** robots.txt answers HTTP 200 and the body is a robots file, not HTML. The parser is lenient, as RFC 9309 asks: unknown lines are ignored, and an empty file is valid.
- **Warn:** robots.txt answers 404, or any other 4xx status. RFC 9309 says crawlers may then access everything, so nothing is blocked, but your intent is unstated.
- **Fail:** the server answers with a 5xx status, the request fails with no response, or a 200 response carries an HTML document (a doctype or an `html` tag near the top). That last case is usually a challenge page or a soft 404 that sends the home page or an error page with status 200.

The scanner does not judge the rules themselves here. Whether those rules let the right crawlers in is the job of later checks.

## How to fix it

Start by fetching the file yourself and looking at the status and the first lines. Most failures have one of three causes: a firewall or bot-protection rule, a routing rule that sends unknown paths to the storefront, or a server error in the code that generates the file.

### WordPress and WooCommerce

- WordPress generates a virtual robots.txt when no physical file exists in the web root. A physical `robots.txt` file overrides it, so check for one first.
- SEO plugins such as Yoast SEO and Rank Math offer a robots.txt editor. Edit the file there so the change survives updates.
- If you write code, use the `robots_txt` filter rather than a static file, so the output stays in step with your settings.
- If robots.txt returns HTML, a caching or security plugin may be serving a cached page or a challenge for it. Exclude `/robots.txt` from page caching and from bot challenges.

### Shopify

- Shopify serves robots.txt for every store from its defaults, so the file is normally present and valid.
- You can customise it with the `robots.txt.liquid` theme template under Online Store, Themes, Edit code. A Liquid error in that template is the most common reason for a broken file, so preview the live output after every edit.
- Apps that manage bots or SEO sometimes edit this template. Recheck the live file after installing or removing one.

### Any other stack

- Serve `/robots.txt` as a static file or a dedicated route that returns status 200 and `Content-Type: text/plain`.
- Make sure your single-page app router or catch-all route does not answer `/robots.txt` with the app shell.
- In your CDN or web application firewall, exempt `/robots.txt` from bot challenges, rate limits and geo blocks. It is a public file that every crawler needs.
- Add a `Sitemap:` line with the absolute URL of your sitemap index. It costs nothing and helps the [sitemap check](/knowledge-base/sitemap-declared-and-reachable).

## Verify it yourself

Check the status, the content type and the start of the body:

```bash
curl -sS -D - -o /dev/null https://example.com/robots.txt
curl -sS https://example.com/robots.txt | head -n 20
```

The first command should show `HTTP/2 200` (or `HTTP/1.1 200`) and a `text/plain` content type. The second should show `User-agent` lines, not markup. Run the same commands with `-A "Googlebot"` to see whether a firewall treats crawlers differently. Google Search Console's robots.txt report shows what Google last fetched.

## Common mistakes

- **A catch-all route answering robots.txt.** Single-page apps and some headless storefronts return the app shell with status 200 for every unknown path. Crawlers find no rules in it.
- **Bot protection on the robots.txt path.** A challenge for robots.txt stops exactly the clients that respect it.
- **Fixing only one host.** `example.com` and `www.example.com` each need their own robots.txt. The scanner reads the file on the host that serves your store.
- **Leaving a staging file live.** A `Disallow: /` copied from a staging site parses perfectly and passes this check, but blocks everything. The [search and assistant crawler check](/knowledge-base/search-and-assistant-crawlers-allowed) catches that.

## FAQ

### Do I need a robots.txt file at all?

Not strictly. Without one, crawlers assume they may read everything. The scanner warns rather than fails, because a missing file cannot declare a sitemap or keep cart and account pages out of crawls.

### What happens if my robots.txt returns a 500 error?

Crawlers that follow RFC 9309 treat the site as fully disallowed while the error lasts. Google documents that it stops crawling the site and later falls back to a cached copy. Fix server errors on this path first.

### Is an empty robots.txt file valid?

Yes. An empty file answered with status 200 parses under RFC 9309 and means every crawler may read everything. It passes this check.

### Does robots.txt need the text/plain content type?

You should send `text/plain`, as Google and RFC 9309 expect. The scanner fails a 200 response only when the body is an HTML document, which is what a challenge page or soft 404 looks like.
