## In short

An agent that reads a catalog sends several requests in a row. If the third one gets 429 Too Many Requests, the agent sees a broken store. This check sends three product reads in a row to the WooCommerce Store API, the public product interface built into WooCommerce, and fails on any 429 or server error. It runs only on WooCommerce stores and has weight 2: expected, not blocking.

## What this check looks at

Rate limiting caps how many requests one client may send in a time window. It protects a store from abuse, and it is useful on endpoints that create orders or try payment cards. On read-only product endpoints, a tight limit mostly stops legitimate readers.

WooCommerce documents its own Store API rate limiter. It is disabled by default, it is configured with the `woocommerce_store_api_rate_limit_options` filter, and it applies to POST requests, not to GET reads. When it is enabled, its default is 25 requests per 10 seconds, and it answers with `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` and, once the limit is hit, `RateLimit-Retry-After` headers. A separate setting limits checkout attempts.

So when product reads are throttled, the cause is usually not WooCommerce itself. It is a firewall, a rule at the CDN (content delivery network, the caching layer in front of the site), a security plugin or the host.

The scanner sends three GET requests, one after the other, to the products endpoint with page sizes of 2, 3 and 4. Different page sizes make each request a distinct URL, so none is answered from the scanner's own cache. It records each status and any rate limit headers: `Retry-After`, the `RateLimit-*` family that WooCommerce uses, and the `X-RateLimit-*` family that proxies and WAFs (web application firewalls) add.

## Why it matters for AI agents

Reading a catalog is never one request. An agent pages through products, opens a few in detail, and compares prices. Three quick reads are a very modest version of that.

When a store throttles that, the agent either gives up or retries slowly. In both cases it gets a partial or stale view of the catalog. Some agents will simply move on to a store that answers.

A limit that protects checkout and write endpoints is good practice. A limit that also blocks anonymous product reads costs the store visibility and buys little protection, because the same data is already public on product pages.

## How the scanner decides

This check runs only on WooCommerce stores. On other platforms it does not run and reports leave it out. It also needs the [Store API to be reachable](/knowledge-base/store-api-reachable): when that check fails, this one is skipped.

The scanner's own HTTP client retries once after a 429 or 503 when the server asks to wait five seconds or less in `Retry-After`, or after one second when that header is absent. The check looks through that retry, so a throttled read that recovered is not hidden.

- **Fail** when any of the three reads ends with 429.
- **Fail** when any read ends with a 5xx server error, or gets no response at all.
- **Warn** when a read succeeded only on the scanner's single retry after a 429 or 503. The Store API throttled the scanner once and recovered.
- **Warn** when all reads succeed but a response signals a limit: a `Retry-After` or `RateLimit-Retry-After` header, or a remaining count of zero.
- **Pass** when all three reads succeed without any of these signals.

The report lists each request with its status and the rate limit headers it carried.

## How to fix it

Scope limits by what the request does. Reads of products and categories should allow normal browsing. Cart writes, checkout and login attempts can be strict.

### WordPress and WooCommerce

- **WooCommerce's own limiter.** It limits POST requests only, so it should not affect product reads. If you enabled it with the `woocommerce_store_api_rate_limit_options` filter and run behind a proxy or CDN, turn on its proxy support so it counts real client addresses instead of the proxy's one address.
- **Security plugins.** Plugins with "rate limiting" or "brute force" protection sometimes count every request to `/wp-json/`. Exclude GET requests to `/wp-json/wc/store/v1/products` and `/wp-json/wc/store/v1/products/categories` from those counters.
- **Server errors.** A 500 or 503 on the third read is often a slow, uncached product query on a busy server. Object caching and fewer heavy product filters help.

### Any other stack in front of WooCommerce

- **WAF and CDN rules.** Find the rule that matches `/wp-json/` and split it. Allow at least ten anonymous GET requests per ten seconds per client on product endpoints. Keep a strict rule on `/wp-json/wc/store/v1/checkout` and cart write endpoints.
- **Host limits.** Some managed hosts throttle the REST API at the server level. Ask them for the limit and for an exception on read endpoints.
- **Send honest headers.** When you do limit, answer 429 with a `Retry-After` header so agents know how long to wait.

## Verify it yourself

Send three reads in a row and print the status and any rate limit headers:

```bash
for n in 2 3 4; do curl -s -o /dev/null -D - "https://example.com/wp-json/wc/store/v1/products?per_page=$n" | grep -iE '^(HTTP|retry-after|ratelimit|x-ratelimit)'; done
```

Each request should answer 200 with no `retry-after` header and no remaining count of zero. Run it from outside your own network, because some firewalls trust known addresses.

## Common mistakes

- **One rule for the whole REST API.** A single limit on `/wp-json/` treats a product read like a login attempt.
- **Counting the CDN instead of the client.** Behind a proxy, every request seems to come from the same few addresses, so a per-address limit trips almost at once.
- **Blocking bots by rate.** A rule meant for aggressive scrapers often catches agents that read only a handful of pages.
- **Answering 429 without Retry-After.** The agent has no idea when to come back, so it usually does not.

## FAQ

### Does WooCommerce rate-limit the Store API by default?

No. WooCommerce documents its Store API rate limiting as disabled by default. When enabled, it applies to POST requests, so product reads with GET are not counted. Throttled reads usually come from a firewall, CDN, plugin or host.

### What rate limit should I allow for product reads?

The scanner's fix suggests at least ten anonymous read requests per ten seconds per client on product endpoints. The check itself only sends three reads in a row, so any limit below that will fail it.

### What does a Retry-After header mean here?

It tells the client to wait before asking again. A product read that carries one signals that the client is close to or over a limit. The scanner warns about it even when the read succeeded.

### Should I rate-limit the checkout endpoint?

Yes, that is where limits protect you from card testing and abuse. WooCommerce has a separate setting for checkout rate limiting. This check never tests checkout.
