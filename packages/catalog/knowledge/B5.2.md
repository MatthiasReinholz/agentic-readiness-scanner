## In short

A UCP (Universal Commerce Protocol) business profile is the JSON file at `/.well-known/ucp` where a store tells agents what it offers. It can exist without offering anything to buy with. This check reads the profile found by the [UCP profile check](/knowledge-base/ucp-business-profile) and asks whether it declares a checkout and at least one payment handler. It carries weight 3, blocking, and runs only when a profile was found. A pass is one of three ways to meet the Level 5 gate, and it lifts the commerce score's cap of 60.

## What this check looks at

UCP splits a store's offer into three maps inside the `ucp` object of `/.well-known/ucp`:

- **Services** are the API surfaces. `dev.ucp.shopping` is the shopping service. Each entry binds it to a transport (`rest`, `mcp`, `a2a` or `embedded`) and usually an endpoint.
- **Capabilities** are features within a service. `dev.ucp.shopping.checkout` is the checkout capability.
- **Payment handlers** describe how an agent can pay: which payment method the store accepts through UCP and how to use it. The UCP payment guide requires an `id` and a `version` on each handler. A `spec` link is optional.

A profile that declares a checkout through REST and accepts one payment handler looks like this:

```json
{
  "ucp": {
    "version": "2026-08-25",
    "services": {
      "dev.ucp.shopping": [
        { "version": "2026-08-25", "transport": "rest", "endpoint": "https://example.com/ucp/v1" }
      ]
    },
    "capabilities": {
      "dev.ucp.shopping.checkout": [{ "version": "2026-08-25" }]
    },
    "payment_handlers": {
      "com.google.pay": [{ "id": "gpay-1", "version": "2026-01-23" }]
    }
  }
}
```

Real entries also carry `spec` and `schema` links, which the specification uses to describe each capability and handler precisely.

## Why it matters for AI agents

An agent that wants to complete a purchase needs two things from the profile: somewhere to send the checkout, and a way to pay. A checkout without a payment handler leaves the agent unable to pay. A payment handler without a checkout has nothing to pay for.

Declaring both is a precondition, not a guarantee. This check reads what the profile says. It does not create a session or test that an order goes through. Agent platforms also decide on their own which merchants they transact with.

Handlers often start in a test environment. A handler whose `environment` is not `production` is declared but not live, and the report names it as such.

Without a declared checkout, an agent can read the store but not buy from it. That is why this check forms the Level 5 gate together with the [ACP discovery document](/knowledge-base/acp-discovery-document) and Shopify's [agentic storefront](/knowledge-base/shopify-agentic-storefront). A pass on any one of the three meets the gate. When none of them passes, the commerce score is capped at 60, however well the rest of the store does. An empty profile is honest for a store that is preparing, but it is not a checkout.

## How the scanner decides

The check is skipped when the UCP profile check failed or recorded no profile. It runs when that check passed or warned, and makes at most one request of its own.

A checkout counts as declared when the profile has a non-empty `dev.ucp.shopping.checkout` capability. A profile that lists no capabilities at all also counts when it has a `dev.ucp.shopping` service with a `rest`, `mcp`, `a2a` or `embedded` transport. A profile that lists capabilities, but only catalog ones, offers no checkout. A payment handler counts when it has a non-empty `id` and `version`.

- **Pass:** a checkout and at least one payment handler are declared.
- **Warn:** only one of the two is declared.
- **Fail:** neither is declared.

Only a pass meets the Level 5 gate and lifts the cap. A warning leaves both in place.

When a `rest` service names an endpoint, the scanner sends a GET request to it and records the status. A REST base URL has no GET resource of its own, so 404 or 405 there is normal and not a finding. Only an endpoint that does not answer at all, or answers with a 5xx error, adds a warning. If the store's robots.txt disallows the endpoint for the scanner, it is not requested, and the report notes that without scoring it.

## How to fix it

Add entries only when the matching integration is live. A declared checkout that fails costs more trust than an empty profile.

### WordPress and WooCommerce

- WooCommerce has no built-in UCP checkout. A UCP extension or a payment provider's integration provides the endpoint and the handlers. Use the profile it generates rather than editing JSON by hand.
- After installing, check that the REST endpoint in the profile answers over HTTPS and is not blocked by a security plugin or by robots.txt.

### Shopify

- Shopify generates the profile, including the shopping service and payment handlers, for eligible stores. You do not edit it.
- Shopify declares its shopping service with the `embedded` transport, which this check accepts. Whether direct checkout is active in a given AI channel is a setting in the Agentic sales channel. See the [agentic storefront check](/knowledge-base/shopify-agentic-storefront).

### Any other stack

- Declare `dev.ucp.shopping.checkout` under `capabilities` and the `dev.ucp.shopping` service with its transport and endpoint under `services`.
- Add each payment handler you accept under `payment_handlers`, with `id`, `version`, `spec` and `schema` as the handler's provider documents them.
- Set handlers to the production environment only when real payments work. Keep test handlers out of the public profile, or expect the report to flag them.
- Make sure the REST endpoint resolves and does not return a 5xx error to a plain GET request.

## Verify it yourself

List the declared capabilities, service transports and handlers:

```bash
curl -s https://example.com/.well-known/ucp | jq '{capabilities: (.ucp.capabilities | keys), services: .ucp.services, handlers: .ucp.payment_handlers}'
```

Confirm that `dev.ucp.shopping.checkout` or a shopping service appears, and that each handler has an `id` and a `version`. Then request the REST endpoint with `curl -si` and make sure it is not a 5xx error.

## Common mistakes

- **Handlers without `id` or `version`.** A handler with only a name and a `spec` link does not count, because the payment guide requires both fields.
- **A sandbox handler in production.** An `environment` of `sandbox` or `test` tells agents the payment path is not live.
- **An endpoint on a host that does not resolve.** Profiles copied from staging often point at an internal hostname.
- **robots.txt disallowing the API path.** Agents that honour robots.txt will not call an endpoint it disallows. Allow the UCP path explicitly.

## FAQ

### What is a UCP payment handler?

It is an entry in the profile's `payment_handlers` map that tells an agent which payment method the store accepts through UCP and how to use it. Each handler needs an `id` and a `version`.

### Why does a 404 on my UCP REST endpoint not fail the check?

The endpoint is a base URL. Requests go to paths below it, so a GET on the base itself often returns 404 or 405. Only no answer or a 5xx error suggests the agent would fail there.

### Does passing this check mean agents can buy from my store?

No. It means the profile declares a checkout and a way to pay. Whether a purchase succeeds depends on the integration behind it and on the agent platform.

### What does the "environment" note on a payment handler mean?

The handler declares an environment other than production, such as a sandbox. Agents should not expect real payments to work through it.
