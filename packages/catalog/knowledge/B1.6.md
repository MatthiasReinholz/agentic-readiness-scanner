## In short

A product feed is only useful while its prices and stock levels are current. This check reads when your public feed last changed, from the HTTP `Last-Modified` header or a date inside the feed. It passes when the feed is under 24 hours old, warns up to 7 days and fails beyond that.

## What this check looks at

The check runs only when the [public product feed check](/knowledge-base/public-product-feed) found a feed. It fetches that feed again and looks for two kinds of timestamp.

- **The `Last-Modified` response header.** RFC 9110, the HTTP semantics standard, defines it as the date the server believes the resource last changed.
- **A timestamp inside the feed.** For RSS that is the channel's `lastBuildDate` or `pubDate`. For Atom it is `updated`. For a JSON feed it is a top-level `updated_at`, `generated_at`, `last_updated` or `updated` field. If the channel has none, the first item's `pubDate` or `updated` is used.

CSV, TSV and JSON Lines files have no standard place for a date. For those formats, the header is the only signal.

## Why it matters for AI agents

An agent that reads a feed treats it as a statement of fact: this item costs this much and is in stock. A stale feed sends the agent to an item that is sold out or priced differently. That costs you the sale and erodes trust in your data.

A clear timestamp also lets an agent decide how much to rely on the feed. A feed marked as rebuilt an hour ago can be used directly. A feed with no date forces the agent to guess or to check every product page anyway.

This check is informational: it is reported but never scored, and it gates no level. No agent channel documents a freshness threshold for feeds it finds on a site, so the scanner shows the age as a hint rather than a verdict. It matters most when you publish a feed and expect agents to use it.

## How the scanner decides

The scanner fetches the feed URL that the feed check accepted.

- **Skip** when the feed check did not find a feed. Its result explains why.
- **Fail** when the feed no longer answers HTTP 200, when it has neither a `Last-Modified` header nor an internal timestamp, or when the timestamps it has cannot be parsed as dates.
- Otherwise the scanner takes the newer of the two timestamps and measures its age against the server's own `Date` header. It falls back to the scanner's clock when that header is missing.
- **Pass** when the age is 24 hours or less.
- **Warn** when it is more than 24 hours and up to 7 days.
- **Fail** when it is older than 7 days.

These thresholds are the scanner's own heuristic. No shopping channel publishes a freshness limit for a merchant-hosted feed. The evidence records both timestamps, which one was used, and the age in hours.

## How to fix it

Two things need to be true. The feed must actually be rebuilt often, and the server must say when that happened.

### WordPress and WooCommerce

- Feed plugins let you set a regeneration schedule. Choose daily at least, or hourly if stock changes often.
- Plugin schedules usually run on WP-Cron, which only fires when someone visits the site. On a quiet store, disable WP-Cron's page-load trigger and run `wp-cron.php` from a real server cron job instead.
- When the plugin writes a static file to `wp-content/uploads`, the web server sets `Last-Modified` from the file's modification time. That is accurate as long as the file is rewritten on each run.
- A caching plugin or CDN may serve an old copy. Exclude the feed URL from page caching, or purge it after each rebuild.

### Shopify

- A feed app that publishes a public file controls the refresh schedule. Check its sync interval in the app settings.
- If the feed is served through an app proxy (a Shopify route that forwards requests to the app's own server), confirm the response carries a `Last-Modified` header or that the XML has a `lastBuildDate`.

### Any other stack

- Run feed generation from a scheduler, not on demand from a request.
- Write the file atomically: build to a temporary name, then rename it. The modification time then reflects a complete build.
- If the feed is generated dynamically, set `Last-Modified` to the time of the newest product change, not the time of the request. A header that always says "now" is not honest and gives agents no information.
- For RSS feeds, set `lastBuildDate` in the channel to the build time.

## Verify it yourself

Read the header and compare it with the current time:

```bash
curl -sI https://example.com/feed/products.xml | grep -i -E '^(last-modified|date):'
```

For an XML feed, check the date inside the file as well:

```bash
curl -s https://example.com/feed/products.xml | grep -o -m1 'lastBuildDate>[^<]*'
```

If both are missing, the check fails no matter how often the feed is rebuilt.

## Common mistakes

- **No date anywhere.** A CSV feed served by an application without a `Last-Modified` header gives the scanner nothing to measure.
- **A cron job that stopped.** The feed plugin was set to daily, but WP-Cron never ran on a low-traffic site.
- **The CDN serves last week's file.** The origin rebuilds correctly, but the edge cache never expires it.
- **A fake "now" timestamp.** Setting `Last-Modified` to the request time makes the feed look fresh while its content is old. It may pass this check, but agents that compare it with your product pages will find the mismatch.
- **An unparseable date.** Use the HTTP date format in the header, such as `Mon, 02 Nov 2026 08:00:00 GMT`, and RFC 822 dates in RSS.

## FAQ

### How often should I regenerate my product feed?

At least once a day. If prices or stock change several times a day, regenerate hourly. The scanner passes a feed that is up to 24 hours old.

### Does Google Merchant Center require a daily feed?

This check does not measure Merchant Center. Merchant Center fetches feeds on the schedule you set in its own settings. The thresholds here apply only to the public copy agents can read on your site.

### My feed is rebuilt every hour but the check says it has no timestamp. Why?

The server does not send `Last-Modified` and the feed carries no date the scanner reads. This is common for CSV feeds and dynamically generated JSON. Add the header, or add a top-level `updated_at` field to a JSON feed.

### Which timestamp wins if the header and the feed disagree?

The newer of the two. The evidence names the one that was used, so you can see which source your feed relies on.
