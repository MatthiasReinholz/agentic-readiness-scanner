## In short

WebMCP is a draft browser API that lets a web page describe its own actions, such as search or add to cart, as tools an AI agent in the browser can call. Its name borrows from MCP (Model Context Protocol), the protocol agents use to call tools on a server. This check looks for WebMCP declarations on the home page and sampled product pages. It is informational and never scored, because the API is still an experiment and no shopping agent documents using it on arbitrary stores.

## What this check looks at

Browser agents today operate a page by reading the screen or the DOM (the tree of elements the browser builds from the HTML) and clicking like a person. That is slow and breaks when a layout changes. WebMCP gives the page a way to say "here is a tool, here is what it does, here are its parameters". The agent can then call the tool directly.

The specification is a draft of the W3C Web Machine Learning Community Group. Chrome and Edge run origin trials, which let sites test the API in real browsers before it ships. It comes in two styles:

- **Declarative.** Attributes on an ordinary HTML form. `toolname` and `tooldescription` go on the form. `toolparamdescription` goes on each field the agent should fill.
- **Imperative.** JavaScript that registers tools through a `modelContext` object, for actions that are not forms.

A declarative search form could look like this:

```html
<form
  toolname="search_products"
  tooldescription="Search the catalog by keyword and return matching products."
  action="/search"
>
  <input name="q" toolparamdescription="Words to search for, such as a product name or brand." />
  <button>Search</button>
</form>
```

Chrome's documentation also describes a `SubmitEvent.agentInvoked` flag. A page can use it to tell when an agent, not a person, submitted the form, and return a result to the agent.

## Why it matters for AI agents

A declared tool is clearer than any amount of visual guessing. An agent that knows `search_products` takes a keyword does not have to find the search box, type and parse the result page.

The audience is still tiny. One shipping consumer is known: ChatGPT's site tools in its desktop browser. No shopping agent documents calling WebMCP tools on stores it has not been set up for. That is why this check is informational: it is reported so you can see what the scanner found, and it never affects your score or level.

Nothing is lost by waiting. Your forms keep working for people and for agents that click.

## How the scanner decides

The scanner reads the HTML and the response headers of the home page and of the product pages it sampled.

- It records every form with a non-empty `toolname` attribute, and whether the form also has a `tooldescription`. Chrome registers no tool when either attribute is missing.
- It counts elements with a `toolparamdescription` attribute.
- It looks for `document.modelContext` or `navigator.modelContext` in inline scripts. The specification now puts the API on `document`, and Chrome's trial still ships both.
- It reads the `Permissions-Policy` header, which turns browser features on or off for a page. The specification defines a `tools` feature, and `tools=()` turns WebMCP off for the page and its frames.

It then decides:

- **Pass:** at least one complete form tool or one inline script using `modelContext` was found. The report lists the tool names and the pages they appear on.
- **Warn:** a form has `toolname` but no `tooldescription`, so the browser never registers it, or a page that declares tools sends `Permissions-Policy: tools=()`, which switches the API off.
- **Not applicable:** no declaration was found on any page. This is the normal result. Absence of an optional feature is not a finding. When the header turns WebMCP off, the report says so, without a penalty.

The scanner does not run JavaScript and does not read external script files. Tools registered from a bundled script are not seen. Use the declarative attributes if you want the scanner to detect them.

## How to fix it

There is nothing to fix. Experiment only if you want to learn how browser agents use your store.

### WordPress and WooCommerce

- The product search form and the add-to-cart form are the natural first candidates. Add the attributes in a child theme template or with a filter on the form's HTML output, so theme updates do not remove them.
- Block themes render the search form from a core block. A small plugin can add the attributes when the block renders.

### Shopify

- Edit the search form and the product form in your theme's Liquid sections under Online Store, Themes, Edit code. Add `toolname`, `tooldescription` and `toolparamdescription` to the existing markup.
- Test in a duplicate theme first. Browsers without the API ignore unknown attributes, so customers see no change.

### Any other stack

- Start with one or two forms whose action is safe and obvious, such as search or newsletter sign-up.
- Write descriptions for a model, not for a person. Say what the tool does, what each field means and what comes back.
- Do not expose actions that spend money or change an account without a confirmation step a person sees.
- Register to the origin trial if you want real browsers to see the tools. Keep the page working for browsers without the API.

## Verify it yourself

Look for the attributes in the served HTML:

```bash
curl -s https://example.com/ | grep -oE 'tool(name|description|paramdescription)="[^"]*"'
curl -sI https://example.com/ | grep -i permissions-policy
```

Each attribute match is a declaration the scanner can see. A `tools=()` in the second command means the page turns WebMCP off. To test the tools themselves, use a Chrome build with the WebMCP origin trial or the early preview, as Chrome's documentation describes.

## Common mistakes

- **Registering tools only from a bundled script.** It may work in the browser, but this scanner reads only inline scripts and attributes.
- **A `toolname` without a `tooldescription`.** The browser registers neither half on its own. Both attributes go on the form.
- **A blanket `Permissions-Policy: tools=()`.** Security headers copied from a template can switch WebMCP off on every page. Allow it with `tools=(self)` where you declare tools.
- **Vague descriptions.** `tooldescription="Form"` tells an agent nothing. Describe the action and its result.
- **Declaring forms that need a login.** An agent that calls the tool without a session gets an error page.
- **Removing visible controls.** WebMCP adds a path for agents. People still need the normal form.

## FAQ

### What is WebMCP?

It is a draft web API from the W3C Web Machine Learning Community Group. It lets a page declare its actions as tools for AI agents running in the browser, with names, descriptions and parameters.

### Is WebMCP the same as an MCP server?

No. An MCP server runs on your infrastructure and agents connect to it over the network. WebMCP tools live inside the page and are called by an agent in the visitor's browser.

### Does WebMCP affect my scanner score?

No. The check is informational. It reports declarations when it finds them and is not applicable when it does not.

### Which browsers support WebMCP?

Chrome and Edge offer it through origin trials. It is not yet a shipped web standard, and other browsers ignore the attributes.
