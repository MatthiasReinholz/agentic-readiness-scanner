## In short

Several new vocabularies let a site state how AI systems may use its content: Content-Signal, the IETF Content-Usage rules, RSL licences and TDM reservations. This check collects the ones your site declares and reports whether each is written correctly. It is informational and never scored, and declaring none is a valid choice.

## What this check looks at

The scanner gathers every usage-preference signal it can find on the site, from four vocabularies:

| Vocabulary                        | Where it lives                                                                                | What a valid value looks like                                                                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Content Signals Policy            | `Content-Signal` lines in robots.txt                                                          | `ai-train`, `search` or `ai-input`, each set to `yes` or `no`, comma-separated, optionally after a path                                                            |
| IETF aipref (AI preferences)      | `Content-Usage` lines in robots.txt, or the `Content-Usage` response header                   | `train-ai`, `ai-use` or `search`, each set to `y` or `n`, as a structured-field dictionary; a robots.txt line may start with a path, the header may not            |
| Really Simple Licensing (RSL)     | a `License` line in robots.txt, or a link with `rel="license"` and type `application/rsl+xml` | robots.txt: an absolute https URL of the licence file; link: an absolute http or https URL                                                                         |
| TDM Reservation Protocol (TDMRep) | `/.well-known/tdmrep.json`, the `tdm-reservation` and `tdm-policy` headers or meta tags       | the JSON file is an array of objects, each with a `location` and a `tdm-reservation` of 0 or 1; the header and meta values are 0 or 1; a policy is an absolute URL |

TDM stands for text and data mining. The headers, meta tags and link elements are read from the home page. The scanner requests `/.well-known/tdmrep.json` once. An HTML page at that address is treated as a soft 404, which means nothing is declared there.

## Why it matters for AI agents

These signals are how a site writes down its terms for machines. A malformed signal is worse than none. A crawler that does read it may discard the whole line, or read a value you did not mean. Either way the preference you think you published is not the one that exists.

The vocabularies are young, and support differs. The IETF Content-Usage vocabulary is still a draft. The Content Signals Policy is a published convention, but no crawler operator documents honouring it. RSL and TDMRep each have their own audiences. That is why this check reports and never scores. It tells you whether what you wrote parses. It does not tell you who obeys it.

The three preference vocabularies share no tokens. `ai-train=no` in a Content-Signal line and `train-ai=n` in a Content-Usage line look alike but belong to different specifications. The scanner never translates one into the other, and you should not assume a crawler does either. If you want a training decision that the major operators have committed to read, the [training-crawler policy check](/knowledge-base/ai-training-crawler-policy) covers the robots.txt groups for that.

## How the scanner decides

- **Not applicable:** no usage-preference signal is declared anywhere. This is a skip, not a failure.
- **Pass:** every declared signal is syntactically valid.
- **Warn:** at least one declared signal is malformed. The message names which kind.

The evidence lists each signal with its source, its value, whether it is valid and, when it is not, the problem. Typical problems are an unknown key, a value other than yes or no (or y or n), a relative licence URL and a tdmrep.json that is not a JSON array.

The weight is informational. The result never changes the score or any level.

## How to fix it

Write each signal in its own vocabulary, check it against that vocabulary's spelling, and do not mix them in one line.

### WordPress and WooCommerce

- Content-Signal, Content-Usage and License lines belong in robots.txt. Add them through the robots.txt editor of your SEO plugin, or through a physical `robots.txt` file if your site uses one.
- Put each Content-Signal or Content-Usage line inside a `User-agent` group, usually the wildcard group.
- A Content-Usage response header or a TDMRep header needs a server rule, a caching plugin's header setting or a small `send_headers` hook in a site plugin.
- `/.well-known/tdmrep.json` is a static file in the web root. Make sure WordPress does not answer that path with an HTML page.

### Shopify

- robots.txt lines go into the theme template `robots.txt.liquid`, under Online Store, Themes, Edit code.
- Shopify does not let a theme add arbitrary response headers or files under `/.well-known/`. Use the robots.txt forms of the signals, or a meta tag in `theme.liquid` for `tdm-reservation`.

### Any other stack

- Add robots.txt lines where the file is generated, and response headers in your web server, CDN or framework middleware.
- If a CDN adds Content-Signal lines for you, check that they sit inside a group and that your own file does not repeat them with different values.
- Serve `tdmrep.json` with a JSON content type and make an unknown `/.well-known/` path answer 404, not your HTML error page with status 200.

## Verify it yourself

Look for every place a signal can live:

```bash
curl -s https://example.com/robots.txt | grep -inE "^(content-signal|content-usage|license):"
curl -sI https://example.com/ | grep -iE "^(content-usage|tdm-reservation|tdm-policy|link):"
curl -s https://example.com/.well-known/tdmrep.json
```

Compare each value with the table above. A tdmrep.json response that starts with HTML means the file does not exist. Rescan to see each signal's verdict in the evidence.

## Common mistakes

- **Mixing vocabularies.** `Content-Usage: ai-train=no` uses a Content-Signal key in a Content-Usage line. Neither specification defines it.
- **Using yes and no in Content-Usage.** The IETF vocabulary uses `y` and `n`. Content-Signal uses `yes` and `no`.
- **Placing a Content-Signal line before any User-agent line.** It then belongs to no group.
- **A relative RSL licence URL.** `License: /license.xml` is malformed. Write the full https URL.
- **A tdmrep.json that is a single object.** The protocol expects an array, even for one rule.

## FAQ

### Do I need Content-Signal or Content-Usage lines?

No. Declaring no usage preference is a valid choice, and the check is then not applicable. Robots.txt groups for training crawlers are the more widely supported way to state a training decision.

### Does Google or OpenAI honour Content-Signal?

No crawler operator documents honouring Content-Signal. That is one reason the scanner reports this check without scoring it.

### What is the difference between Content-Signal and Content-Usage?

Content-Signal comes from the Content Signals Policy and uses `yes` and `no` with keys such as `ai-train`. Content-Usage comes from IETF aipref drafts and uses `y` and `n` with keys such as `train-ai`. They are separate vocabularies with no shared tokens.

### My tdmrep.json returns my 404 page with status 200. Is that a problem?

The scanner treats an HTML response there as no file, so nothing is declared. It is a soft 404 though, which the [unknown URLs check](/knowledge-base/unknown-urls-answer-404) flags for the rest of the site.
