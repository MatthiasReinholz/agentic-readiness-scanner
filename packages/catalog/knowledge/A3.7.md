## In short

Every product URL a store publishes, in its sitemap or in its links, should answer 200 at exactly that address over HTTPS. The `http://` form of the site and the other host variant (with or without `www`) should each redirect once to that one canonical origin. This check follows the sampled product URLs and the host variants, and reports every redirect, downgrade to HTTP and dead sitemap entry it meets.

## What this check looks at

A redirect is an answer with a 3xx status and a `Location` header that sends the client somewhere else. One redirect is cheap. A chain of them, or a redirect that points at a page that no longer exists, costs every crawler time and leaves the index unsure which address is the real one.

The check looks at three things:

- **The sampled product URLs.** The scanner takes them from the sitemap or from links on the home page and records each hop until a final answer. When it found no product URL, it judges the home page instead.
- **The `http://` form of the origin.** For example `http://example.com/`. It should answer one redirect to the HTTPS origin.
- **The other host variant.** If the store lives on `www.example.com`, the scanner requests `https://example.com/`, and the other way round. That variant should also redirect to the canonical origin.

Google documents that it indexes the redirect target, not the URL you listed. Bing asks for canonical URLs in sitemaps and for deleted or redirected URLs to be removed promptly. Google stops following a chain after ten hops.

## Why it matters for AI agents

AI assistants answer from search indexes, and those indexes are built by crawlers that work through a list of URLs with a limited budget. A sitemap full of URLs that redirect makes the crawler spend two requests where one would do. A URL that answers 404 tells the crawler the sitemap cannot be trusted.

Duplicates are the bigger problem. When `http://example.com/product/mug` and `https://www.example.com/product/mug` both answer 200 with the same page, the index holds two copies. Signals such as links and freshness are split between them, and an assistant may cite the address you did not want.

A redirect from HTTPS back to HTTP is worse still. It drops the encryption a buyer expects, and Google documents a preference for HTTPS pages when it picks a canonical URL.

## How the scanner decides

The scanner follows at most five redirects per request. It judges the sampled product URLs first, then the two host variants.

- **Fail** when a redirect leaves HTTPS for HTTP.
- **Fail** when a chain is longer than the five hops the scanner follows.
- **Fail** when a URL taken from the sitemap answers 404 or 410. That is a stale sitemap entry.
- **Warn** when a published URL redirects before it answers, even by one hop. The sitemap or the link should name the final URL. The message reports the longest chain.
- **Warn** when a sampled URL answers a status other than 200 without redirecting.
- **Warn** when the `http://` form or the other host variant serves its own content with 200, answers an error, or redirects to some host other than the canonical origin. A redirect to another host of the same registrable domain is reported as the site being consolidated elsewhere.
- **Pass** when every sampled URL answers 200 at its own address and neither host variant contradicts that.

Some answers are not held against the store. When the home page stands in for product URLs, one redirect from `/` to a locale or landing path such as `/en-us/` is how the site greets every visitor, not a finding. A host variant that answers 429, a gateway error (502, 503, 504) or nothing at all is recorded as inconclusive. When none of the sampled URLs could be fetched, the check is skipped. Every redirect in the report names the URL it left and the one it reached.

This check has weight 2, so it is expected rather than blocking. It does not gate a level on its own.

## How to fix it

Pick one canonical origin first, for example `https://www.example.com`. Every other form of the address should reach it in one 301 (permanent redirect) with the path preserved.

### WordPress and WooCommerce

- Under Settings, General, set both "WordPress Address" and "Site Address" to the canonical HTTPS origin. Mismatches there cause many redirect loops and chains.
- Redirect `http://` and the other host variant at the web server, CDN or host control panel rather than in a plugin, so the redirect happens in one hop before WordPress loads.
- The sitemap that WordPress or an SEO plugin generates uses the permalinks WordPress knows. If product URLs in it still redirect, look for a trailing slash mismatch, an old permalink base, or a language plugin that adds a prefix on request.
- Deleted products leave 404 URLs. Make sure the sitemap is regenerated, and that a page cache does not keep serving an old sitemap.

### Shopify

- Shopify serves the store on its primary domain and redirects other connected domains to it. Check under Settings, Domains that the domain you want is set as primary and that redirection is on for the others.
- Shopify generates `sitemap.xml` from live products, so stale entries are rare. Redirected entries usually come from apps that inject their own sitemaps or from links in theme sections that point at old handles.
- When you change a product handle, Shopify can create a URL redirect. Update links in menus and theme content to the new handle so they stop relying on it.

### Any other stack

- Configure one rule at the edge: any request whose scheme is not HTTPS or whose host is not the canonical host gets a single 301 to `https://` plus the canonical host plus the same path.
- Combine the scheme and host fix into one rule. Separate rules for "add HTTPS" and "add www" produce a two-hop chain.
- Generate the sitemap from the same source of truth that renders product pages, so it can only list URLs that answer 200.
- Never redirect from HTTPS to HTTP, even for a single legacy path.

## Verify it yourself

Follow a product URL from your sitemap and print every hop:

```bash
curl -sIL https://www.example.com/product/stoneware-mug/ | grep -iE '^(HTTP|location)'
```

The output should show a single `HTTP/2 200`. Then check the host variants:

```bash
curl -sIL http://example.com/ | grep -iE '^(HTTP|location)'
curl -sIL https://example.com/ | grep -iE '^(HTTP|location)'
```

Each should show exactly one 301 followed by a 200 on the canonical origin.

## Common mistakes

- **Two rules, two hops.** `http://example.com` goes to `https://example.com`, which then goes to `https://www.example.com`. Merge them into one redirect.
- **Trailing slash drift.** The sitemap lists `/product/mug` and the server redirects to `/product/mug/`. Pick one form and make the sitemap use it.
- **Tracking parameters in published links.** Category pages that link to `?utm_source=` URLs which then redirect to the clean URL turn every product link into a redirect.
- **Forgetting the other host.** The apex domain answers 200 with a copy of the store because only `www` was configured at the CDN.
- **A stale cached sitemap.** Deleted products keep appearing in a sitemap that a cache plugin or CDN serves from an old copy.

## FAQ

### Is one redirect from my sitemap really a problem?

It is not an error, which is why the scanner warns instead of failing. Google indexes the target, not the listed URL, and Bing asks for canonical URLs in sitemaps. Listing the final URL saves every crawler a request and removes doubt about which address is canonical.

### Should I use a 301 or a 302 for http to https?

Use a permanent redirect, 301 or 308. Google documents permanent redirects as a strong signal that the target should be the canonical URL. A temporary 302 tells crawlers the old address may come back.

### Does it matter whether I choose www or the bare domain?

No. Either works. What matters is that you pick one and that the other always redirects to it in one hop.

### Why does a 404 in my sitemap fail the check?

A sitemap is a promise that its URLs are live and canonical. Google asks for sitemaps that list only such URLs, and Bing asks for deleted URLs to be removed promptly. A dead entry wastes crawl budget and makes the whole file less trustworthy.

### Why did the scanner ignore the redirect on my home page?

When no product URL was found, the home page stands in. Most international stores send `/` to a locale path, so one such redirect is treated as normal. A longer chain, or a redirect off the canonical origin, is still reported.
