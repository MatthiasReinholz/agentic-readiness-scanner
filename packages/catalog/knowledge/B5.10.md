## In short

A UCP (Universal Commerce Protocol, an open standard for agents to discover and buy from stores) business profile may publish public keys. Platforms use them to check that a message really comes from the store. This check reads those keys and asks whether each one is public and complete. A key that carries private material fails, because anyone could then sign as the store. The check does not gate a level and does not lift the commerce score's cap.

## What this check looks at

The profile is the JSON file at `/.well-known/ucp`. It may have a top-level `keys` array. That array is a JWK Set as defined in RFC 7517: a list of JSON Web Keys (JWK), each a JSON object that describes one cryptographic key. UCP uses these keys for two things:

- **HTTP Message Signatures.** The sender signs an HTTP message, and the receiver checks the signature with the sender's public key.
- **Signed webhooks.** A webhook is a message a business sends to a platform when something happens, such as an order update. UCP requires webhooks from a business to a platform to be signed.

Each key is made of members, short named fields:

- `kid`, the key id, which verifiers use to look the key up
- `kty`, the key type, such as `EC` (elliptic curve) or `OKP` (the type used for Ed25519 keys)
- `crv`, the curve, such as `P-256` or `Ed25519`
- `x` and `y`, the public coordinates (`OKP` keys have only `x`)
- `use` and `alg`, which are optional

UCP's signatures page requires `kid`, `kty`, `crv`, `x` and `y` for EC keys, and `kid`, `kty`, `crv` and `x` for OKP keys. A public EC key looks like this:

```json
{
  "keys": [
    {
      "kid": "store_2026_11",
      "kty": "EC",
      "crv": "P-256",
      "x": "WbbXwVYGdJoP4Xm3qCkGvBRcRvKtEfXDbWvPzpPS8LA",
      "y": "sP4jHHxYqC89HBo8TjrtVOAGHfJDflYxw7MFMxuFMPY",
      "alg": "ES256"
    }
  ]
}
```

Some members belong only to a private key and must never be published. RFC 7517 and RFC 7518 define them: `d` (the private part of an EC, OKP or RSA key), `p`, `q`, `dp`, `dq`, `qi` and `oth` (RSA), and `k` (a symmetric key of type `oct`, a shared secret).

A verifier must support ES256 (signatures on the P-256 curve). ES384 and EdDSA are optional. A verifier must not reject a key set because it contains a key type or algorithm it does not know. Removing a key from `keys` is how a store revokes it. Releases before 2026-08-25 called the array `signing_keys`. The [UCP profile check](/knowledge-base/ucp-business-profile) warns when a newer profile still uses the old name.

## Why it matters for AI agents

A platform that receives a signed request or webhook from your store reads the `kid`, finds that key in your profile and checks the signature. If the key lacks a member, the platform cannot rebuild the public key. If two keys share a `kid`, it cannot tell which one to use. In both cases your signatures cannot be verified.

A private key in the profile is worse. It is readable by anyone, and anyone who has it can sign messages that look like yours. Deleting the private members afterwards does not help, because the key has already been public. It must be replaced.

Keys are optional in UCP. A profile without them is skipped, not penalised. A pass shows that the published keys are well-formed public keys. It does not show that your store signs its messages, that a signature is valid or that a platform accepts it.

## How the scanner decides

The check uses the keys the [UCP profile check](/knowledge-base/ucp-business-profile) recorded and makes no request of its own. It runs when that check passed or warned, and is skipped when it failed or was skipped.

The scanner looks for a non-empty `keys` array at the top level of the profile, then inside the `ucp` object. If it finds neither, it looks for `signing_keys` in the same two places. Then it checks each key:

- **Private material:** the key has any of the members `d`, `p`, `q`, `dp`, `dq`, `qi`, `oth` or `k`, whatever their value, or its `kty` is `oct`.
- **Completeness:** `kid` and `kty` are non-empty strings. EC keys also need `crv`, `x` and `y`, and OKP keys need `crv` and `x`. Other key types, such as RSA, need only `kid` and `kty` here. An entry that is not a JSON object counts as incomplete.
- **Unique ids:** no two keys share a `kid`.

The verdicts:

- **Fail:** any key carries private material. The report names the key and the members, and says the key must be replaced, not only removed.
- **Warn:** a key is incomplete, or a `kid` is used more than once.
- **Pass:** every key is public and complete.
- **Skip:** the profile publishes no keys, which UCP allows.

Key types, curves and algorithms the scanner does not know are allowed, as the specification says. The scanner does not check that the coordinates form a valid key or that `alg` fits the key, and it verifies no signature.

## How to fix it

### Shopify

- Shopify generates the UCP profile for eligible stores, so any keys in it come from Shopify. You cannot edit them.
- If this check fails or warns on a profile Shopify serves, contact Shopify Support with the report.

### WordPress and WooCommerce

- WooCommerce has no built-in UCP profile. A UCP extension or a payment provider's integration generates it and manages the keys. Update it first.
- If the check still fails or warns, report it to the extension's developer. A fail means the private key is compromised: ask them to replace it, not only to hide the private members.

### Your own UCP implementation

- Generate the key pair on the server. ES256 on the P-256 curve is the safest choice, because every verifier must support it.
- Keep the private key in a secret store that only the signing code can read. Never write it into the profile file.
- Publish only the public members: `kid`, `kty`, `crv`, `x` and `y` for an EC key, or `kid`, `kty`, `crv` and `x` for an Ed25519 key. Add `use` and `alg` if you like.
- Give every key its own `kid`.
- Serve the array as the top-level `keys` of the profile, not as `signing_keys`.

If a private key was ever published, treat it as leaked:

1. Generate a new key pair.
2. Publish the new public key with a new `kid`.
3. Remove the old key from `keys`, which revokes it.
4. Sign with the new private key from now on.
5. Find out how the old key leaked, for example through a build step, a copied file or a log.

## Verify it yourself

Print the published keys, wherever the profile carries them:

```bash
curl -s https://example.com/.well-known/ucp | jq '.keys // .ucp.keys // .signing_keys // .ucp.signing_keys'
```

List the `kid` of every key that carries private material. The answer should be an empty list:

```bash
curl -s https://example.com/.well-known/ucp | jq '[(.keys // .ucp.keys // .signing_keys // .ucp.signing_keys // [])[] | select(has("d") or has("p") or has("q") or has("dp") or has("dq") or has("qi") or has("oth") or has("k") or .kty == "oct") | .kid]'
```

Then check by eye that every key has `kid`, `kty`, `crv` and `x`, that EC keys also have `y`, and that no `kid` appears twice.

## Common mistakes

- **Publishing the private export.** A private JWK has the same members as the public one plus `d`, so the wrong export is easy to miss.
- **Using a shared secret.** A symmetric `oct` key signs and verifies with the same value. It can never be public.
- **Deleting `d` and keeping the key.** The private key was already exposed. Replace the key pair.
- **Reusing a `kid`.** A new key needs a new id, or verifiers may pick the wrong key.
- **An EC key without `y`.** EC keys need both coordinates.
- **The old array name.** Profiles at version 2026-08-25 or later use `keys`, not `signing_keys`.

## FAQ

### Do I have to publish keys in my UCP profile?

No. UCP says a profile may publish them, and this check is skipped when there are none. UCP does require webhooks from a business to a platform to be signed, and the `keys` array is where a profile publishes the public keys that verify them.

### What is a kid?

It is the key id, a name you choose for each key. A signed message carries the `kid`, and the verifier uses it to find the matching public key. Each key needs its own.

### Which key type should I use?

An EC key on the P-256 curve with the ES256 algorithm. Every UCP verifier must support ES256. ES384 and EdDSA are optional, so not every platform can verify them.

### Why does the check fail instead of warn when it finds a private key?

Anyone who reads your profile can copy the private key and sign messages as your store. Removing it from the file does not undo that. The key pair has to be replaced.

### Will a platform reject my keys if it does not know the key type?

UCP says a verifier must not reject a key set because of a key type or algorithm it does not know. This check allows them too. A platform can still only verify signatures made with an algorithm it supports.
