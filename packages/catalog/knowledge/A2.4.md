## In short

An AI agent that fetches your store with a truthful user agent should get the page, not a challenge, a CAPTCHA or a 403. If your home page, robots.txt or product pages refuse such a client, the store is unreachable for every agent that is not on an allow list. This check reports what an honestly identified client meets, and it is a Level 1 gate.

## What this check looks at

The scanner identifies itself as `AgenticReadinessScanner` with its version and a documentation URL. It never pretends to be a browser or another crawler. This check inspects the answers it got for the pages an agent needs: the home page, robots.txt, the sampled product pages and the policy pages it found on the same origin.

A page counts as blocked when one of these is true:

- It answered with HTTP status 401, 402, 403, 406, 429 or 451.
- It carried a challenge marker: the `cf-mitigated: challenge` or `x-vercel-mitigated: challenge` header, a DataDome captcha, or a small page with challenge wording such as "Just a moment" or "Verify you are human".
- It was a denial page standing in for the content, for example a short "Access denied" page served with status 200.

When the response reveals the product behind it, the message names it: Cloudflare, Akamai, DataDome, Vercel, Imperva, HUMAN (PerimeterX), AWS WAF or Fastly. A WAF is a web application firewall.

The check also notes a softer problem. A page that redirects to a consent screen or a country picker instead of its content is an interstitial.

## Why it matters for AI agents

An agent that shops for a person does what a careful script does. It sends a request, reads the HTML and moves on. It does not solve CAPTCHAs, run challenge scripts or click through cookie walls. A challenge is a closed door to it.

Bot management is usually set up to stop scrapers and credential stuffing. Many rule sets also block any client that is not a known browser. That catches assistants fetching a page because a person asked, new agents that are not on any allow list yet, and tools like this scanner. Some large crawlers get through because they are verified by published IP ranges or signed requests. Most agents are not.

Google's guidance on intrusive interstitials makes a related point for people: a page that hides its content behind a full-screen gate is a worse result. For an agent without cookies, a consent redirect can mean it never sees the content at all.

## How the scanner decides

- **Fail:** the home page, robots.txt or any sampled product page is blocked.
- **Warn:** nothing essential is blocked, but at least one page redirected to a consent or region interstitial.
- **Pass:** no block, challenge or interstitial. A policy page that alone refuses the scanner still passes, with a note. The [agent-readable policy pages check](/knowledge/agent-readable-policy-pages) reports that cost.
- **Skipped:** no page could be fetched at all.

A page that could not be fetched, such as a dropped connection, is reported as unfetched and never counted as a block.

A home page that refuses the scanner still produces a report. This check fails, robots.txt and the sitemap are evaluated, and every check that needs the pages is marked not evaluated.

The scanner meets what any unverified agent meets. If your rules let verified crawlers through, the message says that they may fare better.

This check has weight 3, which means blocking. It is a gate for Level 1 and every level above it.

## How to fix it

Keep strict rules where they belong, on login, cart, checkout and account paths. Relax them on the pages an agent reads: product, category, policy and `/.well-known/` paths, plus robots.txt and the sitemap.

### WordPress and WooCommerce

- Security plugins with firewall features often block unknown user agents or rate-limit hard. Look for "block fake bots", "block unknown crawlers" or similar settings and turn them off for public pages.
- If a hosting firewall sits in front of WordPress, check its bot rules too. Managed WordPress hosts often run one.
- Cookie consent plugins should show a banner over the page, not redirect to a separate consent URL.

### Shopify

- When a Shopify store blocks an honest client on product pages, the cause is often a proxy, CDN or bot-protection app placed in front of the store. Start there.
- Review any bot-protection or "anti-scraping" app and its rules for product pages.
- A storefront password or a region redirect app will also stop agents. Make sure product pages answer directly for visitors without cookies.

### Any other stack

- In Cloudflare, review the Bot Fight Mode or Super Bot Fight Mode settings and any WAF custom rules that challenge non-browser clients. Use skip rules for product and policy paths rather than switching protection off everywhere.
- In Akamai, DataDome, Imperva, HUMAN or AWS WAF, look for rules that act on "unverified bots" or on user agents that are not browsers. Lower the action from challenge or block to monitor on public read paths.
- Keep rate limits, but allow a handful of polite requests in a row. A 429 after three page loads blocks every agent.
- Serve the content to clients without cookies. Consent and region choices can be overlays.

## Verify it yourself

Request a product page the way an honest agent would, with no cookies and a non-browser user agent:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -A "AgenticReadinessScanner/1.0 (+https://github.com/MatthiasReinholz/agentic-readiness-scanner)" https://example.com/products/example
curl -sI -A "AgenticReadinessScanner/1.0" https://example.com/robots.txt | grep -iE "^(http|cf-mitigated|x-vercel-mitigated|server|location)"
```

A 200 with real HTML is what you want. A 403, a 429, a `cf-mitigated` header or a redirect to a consent path means agents are being stopped. Repeat from a server outside your office network, since some rules allow known IP addresses.

## Common mistakes

- **Testing only in a browser.** Your browser has cookies, runs JavaScript and passes challenges silently. An agent does none of that.
- **Allow-listing a few famous crawlers and calling it done.** Verified crawlers get through, but assistants fetching for a person and new agents do not.
- **Blocking robots.txt itself.** If robots.txt answers 403, no agent can even learn your rules.
- **Serving a block page with status 200.** It hides the problem from monitoring, and the scanner still counts it as a block.
- **Redirecting to a consent page.** An agent without cookies lands on the consent page every time and never reaches the product.

## FAQ

### Why does my site block the scanner but not Googlebot?

Googlebot is verified by its published IP ranges, and most bot-management products let verified search crawlers through. The scanner is not verified, so it meets the same rules as any new agent or assistant fetcher.

### Will allowing honest agents let scrapers in?

Scrapers that tell the truth about who they are can be rate-limited or blocked by name. Most abusive traffic hides behind browser user agents. You can keep strict rules on cart, checkout and account paths and still let polite clients read product pages.

### Is a 429 really a block?

For this check, yes. A store that rate-limits an honest client after a few requests is unreachable for that client. Allow a small burst and slow down only sustained high rates.

### Does a cookie banner count as a block?

A banner drawn over the page does not. A redirect to a separate consent or country page before the content is an interstitial, and the check warns about it.
