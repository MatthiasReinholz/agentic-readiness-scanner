## In short

This check records how an Adobe Commerce (Magento) storefront is built: a theme on the stack of Adobe's Luma and Blank themes, a Hyvä theme, or a headless front end that reads the store's data through an API. It also names the theme by its Vendor/theme path. The result is informational and never scored. It tells you where the fixes from the other checks belong.

## What this check looks at

Adobe Commerce ships two default themes: Luma, a demonstration theme that may be used live, and Blank, a basis for custom themes. Themes built on them load their scripts through RequireJS, a JavaScript module loader. Hyvä is a separate theme family built on Tailwind CSS and Alpine.js instead.

The check reads the home page the scan already fetched. It makes no extra request.

| Trace                                                                                   | What it shows                                                                                                            |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| assets under `/static/frontend/<Vendor>/<theme>/` (with an optional `version…` segment) | the theme that renders the page                                                                                          |
| a `Hyva/` theme path, or the `window.hyva` object                                       | a Hyvä theme. Hyvä prints that object on every page, so a Hyvä child theme under another vendor's name is recognised too |
| RequireJS or `text/x-magento-init` scripts                                              | a theme on the Luma and Blank stack                                                                                      |
| a framework's own markers, with no theme path and no RequireJS                          | a headless front end, such as a Next.js or Nuxt storefront                                                               |

## Why it matters for AI agents

Agents read the HTML a store serves. Luma-based and Hyvä themes both render product pages on the server, so their content arrives complete. A headless front end may render on the server or in the browser, and only the first serves complete pages to an agent that does not run JavaScript. [Server-rendered content](/knowledge-base/server-rendered-product-content) checks that, whatever the storefront.

How heavy a page is depends on the theme and its extensions, which [page weight](/knowledge-base/page-weight-crawler-limits) measures. The build also decides where a fix goes:

- In a Luma-based or Hyvä theme, structured data and meta tags live in the theme's layout XML and templates.
- In a headless front end, the front-end application renders every page, so fixes go into its code.

## How the scanner decides

This check runs only when the scan recognised Adobe Commerce (see [platform detection](/knowledge-base/ecommerce-platform-detection)). It has weight `info`: it is reported, never scored, and gates no level.

1. A `Hyva/` theme path or the `window.hyva` object means a Hyvä theme.
2. Otherwise, RequireJS or `text/x-magento-init` scripts mean a Luma-based theme.
3. Otherwise, a theme path alone names the theme without a family.
4. Otherwise, a recognised JavaScript framework means a headless front end.

It always passes when it runs. The fact appears at the top of the report next to the platform, for example "Theme: Hyvä (Hyva/default)" or "Theme: Luma-based theme (Acme/fashion)". When none of the traces is there, no fact is recorded.

## How to fix it

There is nothing to fix. If you want to change the storefront, these are the usual paths.

### Adobe Commerce

- **Customising a theme.** Create a child theme under `app/design/frontend/<Vendor>/<theme>` and override only the files you change. Never edit Luma or Blank directly, because upgrades overwrite them.
- **Moving from Luma to Hyvä.** Hyvä needs compatible versions of the extensions that render on the storefront. Compare product pages for prices, structured data and links before switching.
- **Going headless.** Make sure the front end renders product content, prices and structured data on the server.

## Verify it yourself

Look for the theme path, RequireJS and Hyvä's object:

```bash
curl -s https://example.com/ | grep -oE '/static/(version[0-9]+/)?frontend/[A-Za-z0-9_-]+/[A-Za-z0-9_-]+/|requirejs/require(\.min)?\.js|text/x-magento-init|window\.hyva' | sort | uniq -c
```

In the admin, Content > Design > Configuration shows the theme applied to each store view.

## Common mistakes

- **Taking the theme name for its family.** A theme called `Acme/default` can be Luma-based or Hyvä. The scripts it loads decide.
- **Assuming Hyvä is required for agents.** A well-built Luma theme serves agents complete pages too.
- **Assuming a headless front end is invisible to agents.** One that renders on the server serves complete pages.

## FAQ

### How can I tell if a Magento store uses Hyvä?

Hyvä prints a `window.hyva` object on every page, and its default theme loads from a `Hyva/` theme path. A Luma-based store loads RequireJS instead.

### Is Hyvä better for AI agents than Luma?

Not in what agents can read: both render product pages on the server. What agents need is complete HTML with prices, structured data and working links, and either theme family can deliver or miss that.

### Why does the report show the theme path but no family?

The page loads assets from a theme folder, but neither RequireJS nor Hyvä's object. That happens with themes that bundle their scripts differently, such as some performance themes.
