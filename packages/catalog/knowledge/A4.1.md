## In short

An MCP server card is a small JSON file that tells an agent where a site's Model Context Protocol (MCP) server lives and how to connect. This check looks for a card through the routes the MCP Server Card extension describes, mainly an entry in `/.well-known/ai-catalog.json`. It is a nice-to-have: most stores have no MCP server, and no MCP host probes these files yet.

## What this check looks at

MCP is an open protocol, published at modelcontextprotocol.io, that lets an AI application call tools and read data from a server. A store could run an MCP server that offers product search or order lookup. The protocol itself does not say how an agent finds that server for a given domain.

The MCP Server Card extension fills that gap. Its proposal, SEP-2127, describes a static card with the server's identity (`name`, `version`, `description`) and its remote endpoints under `remotes`. The detailed format lives in an experimental extension repository. It names two routes:

- **An AI Catalog** at `/.well-known/ai-catalog.json`. This is a protocol-neutral list of AI artifacts on a domain. An entry of type `application/mcp-server-card+json` either links to a card or embeds it.
- **The endpoint itself.** The recommended location for a card is `{endpoint}/server-card`, for example `https://example.com/mcp/server-card` for an endpoint at `https://example.com/mcp`.

A card that follows the extension's schema looks like this:

```json
{
  "name": "com.example/shop",
  "version": "1.0.0",
  "description": "Product search and order status for Example Shop",
  "remotes": [{ "type": "streamable-http", "url": "https://example.com/mcp" }]
}
```

The schema also requires a `$schema` field that points at the extension's JSON Schema. The extension's discovery document asks hosts to serve cards with `Access-Control-Allow-Origin: *` and a public cache lifetime.

## Why it matters for AI agents

Today people connect agents to MCP servers by pasting a URL or picking one from a registry. A card makes that automatic. An agent or a registry that knows only your domain could read the catalog, find the card and connect without anyone typing an endpoint.

That is the promise, not the present. No MCP host documents probing these files on arbitrary sites yet. That is why the check carries weight 1, nice to have. It does not gate any level.

A store should publish a card only when it actually runs an MCP server that outside agents may use. A card for a server that does not exist is worse than no card. If your platform runs the server for you, as Shopify does with its storefront catalog endpoint, the [agentic storefront check](/knowledge-base/shopify-agentic-storefront) is the one that matters.

## How the scanner decides

The scanner tries the documented routes in order and stops at the first card that parses. A card parses when it has a name and at least one http or https endpoint URL. It accepts `endpoint`, `url` or a `url` inside `remotes`, `transports` or `endpoints`.

1. It reads `/.well-known/ai-catalog.json` and looks at up to two entries of type `application/mcp-server-card+json`. An embedded card counts, and so does a card at the entry's `url`.
2. It collects endpoint hints: a `Link` header with `rel="mcp-server"` on the home page, and links in `/llms.txt` whose path contains "mcp". Only hints on your own host or its subdomains count. It probes `{hint}/server-card` for up to two hints.
3. It tries two community paths: `/.well-known/mcp/server-card` and the older `/.well-known/mcp/server-card.json`.

- **Pass:** a card was found through the AI Catalog or at `{endpoint}/server-card`.
- **Warn:** a card was found only at one of the community paths. The extension's discovery document discusses `/.well-known/mcp/server-card` and recommends against it. The specification defines neither path.
- **Fail:** no card was found anywhere.
- **Inconclusive:** a card URL answered 401, 403, 429 or another refusal, a bot-management challenge, or failed transiently. The report names the URL and the refusal instead of claiming there is no card.

The endpoint found here feeds two follow-up checks: [MCP endpoint reachable](/knowledge-base/mcp-endpoint-reachable) and [OAuth discovery for MCP](/knowledge-base/oauth-discovery-for-mcp).

## How to fix it

First decide whether you run an MCP server that outside agents should use. If not, leave this check failing. It costs little.

### WordPress and WooCommerce

- WordPress does not serve `/.well-known/ai-catalog.json` on its own. Place a static file in the web root under `.well-known/`, or add a rewrite rule in a small plugin that returns the JSON.
- If an MCP plugin exposes your store, find its endpoint URL in the plugin settings. Check whether the plugin already serves `{endpoint}/server-card`. If it does, list that URL in the catalog.
- Serve the card with the `application/mcp-server-card+json` content type. Make sure caching plugins do not rewrite it into HTML.

### Shopify

- Shopify runs an MCP endpoint for eligible stores at `/api/ucp/mcp` and advertises it through UCP, not through a server card.
- Shopify themes offer no standard way to publish your own files under `/.well-known/`, so there is nothing to fix here. Focus on the [agentic storefront check](/knowledge-base/shopify-agentic-storefront).

### Any other stack

- Serve the card at `{endpoint}/server-card` from the same service that runs the MCP server, so the two stay in sync.
- Add an entry to `/.well-known/ai-catalog.json` that points at it. The extension's discovery document suggests the `application/ai-catalog+json` content type for the catalog.
- Link the endpoint from `/llms.txt`, or send a `Link` response header with `rel="mcp-server"` that points at it, as an extra hint.

## Verify it yourself

Read the catalog and the card:

```bash
curl -s https://example.com/.well-known/ai-catalog.json
curl -s -H "Accept: application/mcp-server-card+json" https://example.com/mcp/server-card
```

The card should be JSON with a `name` and a `remotes` entry whose `url` is your endpoint. Rescan to confirm the verdict.

## Common mistakes

- **Only using `/.well-known/mcp/server-card.json`.** Several blog posts recommend it. It is not part of the specification, so the check warns.
- **A card that points at a documentation page.** The endpoint URL must be the MCP endpoint itself, not a page about it.
- **A firewall rule that challenges the card URL.** Agents fetch it without a browser. A challenge makes the card invisible, and the scanner reports the result as inconclusive.
- **Listing tools in the card.** The extension deliberately leaves tools out, because they can differ per user. Agents read them from the live server.

## FAQ

### Does my online store need an MCP server?

Not to be found or recommended by AI assistants. Those rely on crawlable pages, structured data and feeds. An MCP server helps only when you want agents to call live functions, such as stock lookups, and are ready to run and secure it.

### Where should an MCP server card live?

At `{endpoint}/server-card`, listed in `/.well-known/ai-catalog.json`. Those are the two routes the MCP Server Card extension describes. The `/.well-known/mcp/` paths are community conventions.

### Will ChatGPT or Claude find my MCP server through the card?

No MCP host documents doing that today. Users add servers by URL or through registries. The card prepares for automatic discovery but does not trigger it.

### Is the server card part of the MCP specification?

It is an extension, not part of the core protocol. SEP-2127 charters it, and the wire format is maintained in a separate extension repository.
