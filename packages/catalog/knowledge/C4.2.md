## In short

Some accessibility barriers are visible in the raw HTML: a missing page language, images without alt text, form fields without labels, icon buttons without a name, and a viewport that blocks zoom. This check reads the home page and sampled product pages for these basics. Passing it does not make a site accessible. Automated checks find only a minority of barriers, and contrast, keyboard use and focus need a rendered page. It is a technical signal, never scored, and not legal advice.

## What this check looks at

The items come from the Web Content Accessibility Guidelines (WCAG) 2.1, the W3C standard most accessibility laws point to:

- **Page language:** the `html` element declares a `lang`, so screen readers pronounce the text correctly.
- **Page title:** the page has a `title`, which names the tab and is the first thing a screen reader announces.
- **Image alt text:** content images have an `alt` text. Decorative images may have an empty `alt=""`, which tells assistive technology to skip them.
- **Form labels:** each form control has a `label` or an accessible name from `aria-label` or `aria-labelledby`.
- **Named links and buttons:** each link and button has an accessible name, from its text or an ARIA attribute.
- **Zoom allowed:** the viewport tag does not set `user-scalable=no` or a `maximum-scale` below 2, so people can enlarge text to 200 percent.

Which laws expect an accessible store, by market:

- **European Union:** the European Accessibility Act (EAA), Directive (EU) 2019/882, has applied to e-commerce services for consumers since 28 June 2025. The usual technical reference is EN 301 549, whose web requirements match WCAG 2.1 Level AA. Germany's version is the BFSG.
- **United States:** Title III of the Americans with Disabilities Act (ADA) covers public accommodations. No regulation sets a technical web standard for private businesses; courts decide case by case, and WCAG is the usual benchmark in settlements. California's Unruh Civil Rights Act is often added to such claims.
- **Ontario (Canada):** the AODA's Integrated Accessibility Standards Regulation requires organizations with 50 or more employees to meet WCAG 2.0 Level AA on their public websites, with two exceptions.
- **United Kingdom:** the Equality Act 2010 requires service providers to make reasonable adjustments for disabled people, which includes websites.
- **Australia:** the Disability Discrimination Act 1992 makes it unlawful to discriminate in providing goods and services, which the Australian Human Rights Commission applies to websites.
- **Brazil:** Article 63 of the Brazilian Inclusion Law (LBI) requires accessible websites; the national standard ABNT NBR 17225:2025 sets out the technical requirements.

The report lists every law with a link to its official text.

## Why it matters for AI agents

Browsing agents navigate through the accessibility tree. That tree is what a browser builds from the HTML for assistive technology: every element with its role, its accessible name and its state. The labels, names, alt text and language this check reads are literally what these agents read.

The documentation says so directly:

- OpenAI's [publishers and developers FAQ](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq) says the agent in its Atlas browser uses ARIA labels and roles, the ones that support screen readers, to interpret page structure and interactive elements, and that making a site more accessible helps it.
- Microsoft's [Playwright MCP](https://github.com/microsoft/playwright-mcp) server, a common way to give an AI model a browser, works from Playwright's accessibility tree rather than screenshots.
- Google's [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md) server takes page snapshots based on the accessibility tree.

An "Add to cart" button that is only an icon has no name in that tree. The agent sees a button and nothing else. A size dropdown without a label is an unnamed list. A search field without a name is just an input. Agents that work from screenshots, such as Anthropic's [computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool), rely on what is visible instead, so visible labels help them too. Either way, the fixes that help screen reader users help agents.

## How the scanner decides

The check reads the home page and the sampled product pages, using the server-rendered HTML without running JavaScript. Each page is judged on the six items above.

- **Found:** every page passes every item.
- **Review:** some items fail on some pages. The evidence names the item, the page and examples, such as an image file without alt text or an unnamed button.
- **Not found in the pages read:** most items fail.

What it cannot see:

- Colour contrast, keyboard operation, focus order and visible focus. These need a rendered page and often a person.
- Whether alt text is accurate or useful. An alt text of "image" passes.
- Content added by JavaScript after load, such as a variant picker built in the browser.
- Checkout, account pages and anything behind a login.

Automated checks, including this one, find a minority of accessibility barriers. Passing never shows WCAG conformance. The mobile viewport and main landmark items are covered for readiness by the [mobile viewport check](/knowledge-base/mobile-viewport) and the [main content check](/knowledge-base/accessible-main-content).

## How to fix it

Fix the templates once rather than page by page, then fill in the content fields that templates read, such as image alt text.

### WordPress and WooCommerce

- Set the site language under Settings, General. Most themes print it as the `html` `lang` through `language_attributes()`.
- Add alt text to product images in the Media Library, in the Alternative Text field. WooCommerce uses it for the gallery. The [image alt text check](/knowledge-base/product-image-alt-text-and-resolution) covers product images in markup.
- Check the theme's search, newsletter and quantity fields for labels, and icon buttons (cart, search, menu) for names. Themes in the WordPress.org directory with the accessibility-ready tag have been reviewed for these basics.
- Look for `user-scalable=no` in `header.php` or a theme setting, and remove it.

### Shopify

- Shopify sets the `lang` from the store's language. Check that a custom theme prints `lang="{{ request.locale.iso_code }}"` on the `html` element.
- Add alt text to product media: open the product, select the image and choose Add alt text.
- Shopify's own themes label their controls. Apps that inject buttons or forms, such as wishlists, reviews or pop-ups, are where unnamed controls often come from. Check them.

### Any other stack

- Set `lang` on the `html` element per locale, and a unique `title` per page.
- Use native elements: `button` for actions, `a` for navigation, `label` for fields. Use `aria-label` only where no visible text exists.
- Mark decorative SVG icons with `aria-hidden="true"` and name the control that contains them.
- Use `width=device-width, initial-scale=1` as the viewport and nothing that blocks zoom.

## Verify it yourself

Run a free automated tool against your home page and a product page: the Lighthouse accessibility audit in Chrome DevTools, the [axe DevTools](https://www.deque.com/axe/devtools/) extension, or [WAVE](https://wave.webaim.org/). In Chrome DevTools, the Elements panel's Accessibility pane shows the accessibility tree, which is what browsing agents read.

A quick look at the raw HTML:

```bash
curl -s https://example.com/ | grep -oiE "<html[^>]*lang=\"[^\"]*\"" | head -1
curl -s https://example.com/ | grep -oiE "<meta name=\"viewport\"[^>]*>"
curl -s https://example.com/ | grep -oiE "<img[^>]*>" | grep -vic "alt="
```

The last command counts images without an `alt` attribute. Then test with a keyboard: tab through the page and check that you can reach and see every control.

## Common mistakes

- **Alt text that repeats the file name.** "IMG_4032.jpg" is not a description.
- **Placeholder text as the only label.** It disappears when typing and is not a reliable name.
- **Icon-only cart, search and menu buttons.** They need an `aria-label` or hidden text.
- **Blocking zoom to "fix" layout on phones.** Fix the layout instead; people need to enlarge text.
- **One `lang` for all languages.** A German page served with `lang="en"` is read with English pronunciation.
- **Treating a pass as conformance.** These are six items out of dozens of WCAG criteria.

## FAQ

### Does this apply to my store?

In the EU, the EAA covers e-commerce services offered to consumers, except microenterprises providing services: fewer than 10 persons and an annual turnover or balance sheet total of no more than EUR 2 million. In Ontario, the WCAG 2.0 Level AA duty applies to organizations with 50 or more employees. In the US, UK, Australia and Brazil, the duty comes from general anti-discrimination and inclusion laws, without a size threshold for websites. The scan cannot tell which applies to you; ask a lawyer.

### Why does the check say "review" when only one image lacks alt text?

Found means every page passes every item. One failure moves the result to review, and the evidence names the image so you can fix it.

### Is empty alt text a failure?

No. `alt=""` is the correct way to mark a decorative image, and the check accepts it. A missing `alt` attribute is what fails.

### Will passing this check protect me from accessibility complaints?

No. It covers a small static subset. Contrast, keyboard use, focus, captions and the checkout all matter and are not checked here.

### Does an accessibility overlay fix these items?

An overlay may add some attributes in the browser, after the HTML that this check and many agents read. It does not make a site conformant. See the [overlay check](/knowledge-base/accessibility-overlays).
