## In short

security.txt is a small text file that tells security researchers how to report a vulnerability on your site. RFC 9116, the internet standard for the file, defines it. This check reads `/.well-known/security.txt` and reports whether it has a contact and a valid expiry date. It is informational: it never affects your score or level.

## What this check looks at

The file lives at a fixed address on your host:

```text
https://example.com/.well-known/security.txt
```

It is plain text made of `Field: value` lines. RFC 9116 requires two fields:

| Field     | Meaning                                                                                                                    |
| --------- | -------------------------------------------------------------------------------------------------------------------------- |
| `Contact` | How to report a problem: a `mailto:` address, a `tel:` number or an `https://` URL. It may appear more than once.          |
| `Expires` | The date and time after which the file should no longer be trusted, in the RFC 3339 format such as `2027-06-01T00:00:00Z`. |

Optional fields include `Preferred-Languages`, `Policy` (a link to your disclosure policy), `Acknowledgments`, `Encryption` and `Canonical`. The RFC recommends an expiry less than a year in the future, so the file gets reviewed regularly.

## Why it matters for AI agents

It mostly does not, and the scanner says so. security.txt is a sign of operational maturity: someone has thought about how a security problem would reach them. No agent or merchant programme the scanner tracks reads it to decide whether to recommend or buy from a store.

That is why the check has the weight "info". It is reported so you have the full picture, but it never adds or removes points and it is not part of any level. If you are prioritising, every scored check comes first.

## How the scanner decides

The scanner requests `/.well-known/security.txt` once on the store's origin.

- **Pass:** the file answers HTTP 200 with a body that is not an HTML page, has at least one `Contact` field, and has an `Expires` field with a date in the future.
- **Warn:** the file exists but has no `Contact` field, its `Expires` field is missing or cannot be read as a date, or the date has passed.
- **Not applicable:** the file does not answer HTTP 200, or the response is an HTML page, which often means a catch-all page answered instead. An absent file is nothing to evaluate, because the file is optional.

The scanner does not check the content type, signatures, the `Canonical` field or the legacy location at the site root.

## How to fix it

Only if you want a disclosure channel. Decide who receives reports, then publish the file.

### WordPress and WooCommerce

- Upload a `security.txt` file to a `.well-known` folder in the web root, next to `wp-config.php`. Your host's file manager or SFTP works.
- Some security plugins can generate the file for you. Check that the result is served as plain text at the exact path.
- Put a reminder in your calendar to renew the `Expires` date before it passes.

### Shopify

- Shopify's admin has no standard setting for files under `/.well-known/` on the storefront domain. If you need a security.txt and cannot serve it there, publish your security contact on your contact page instead.
- This has no effect on your score.

### Any other stack

- Serve the file at `/.well-known/security.txt` with the `text/plain` content type, over HTTPS.
- Include at least `Contact` and `Expires`. Add `Policy` if you publish a disclosure policy.
- Generate the `Expires` date in your deployment pipeline, or set a reminder, so the file never goes stale.

## Verify it yourself

Fetch the file and look at its fields:

```bash
curl -si https://example.com/.well-known/security.txt | head -20
```

Check that the status is 200, the content type is `text/plain`, and the `Expires` date is in the future. The website securitytxt.org also offers a free generator.

## Common mistakes

- **An expired file.** An `Expires` date in the past tells readers the file is stale. The check warns.
- **A date in the wrong format.** Write the date in RFC 3339 format with a time and time zone.
- **A catch-all page at the path.** Some sites answer every unknown URL with the home page. The scanner treats an HTML response as no file.
- **A contact nobody reads.** An address that bounces or is never checked is worse than no file.

## FAQ

### Is security.txt required?

No. RFC 9116 describes it as a way to help researchers reach you, not an obligation. The scanner never scores it.

### Does security.txt affect AI search or agent readiness?

Not as far as any documented consumer shows. The scanner reports it as operational maturity only, with the weight "info".

### What should the Expires date be?

A date in the future, and RFC 9116 recommends less than a year ahead. Update it whenever you review the file.

### Can I put security.txt at the site root instead?

The standard location is `/.well-known/security.txt`. RFC 9116 allows the root location only for legacy compatibility, and the scanner checks only the standard one.
