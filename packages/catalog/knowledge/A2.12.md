## In short

Salesforce B2C Commerce, also known as Salesforce Commerce Cloud, sets robots.txt per instance type in Business Manager. The preset meant for development and staging blocks crawlers, and because robots.txt is a site preference it can travel to production with a replication. This check fails when your storefront's robots.txt shuts out Googlebot and Bingbot everywhere, or blocks `/on/demandware.static/`, where the storefront's scripts, styles and images live.

## What this check looks at

Salesforce documents the robots.txt settings in Business Manager under App Launcher, Merchant Tools, your site, SEO, Robots. There you choose "Define robots.txt Specific to Instance Type" and pick one of three options per instance:

| Option                                                | Meant for                                        |
| ----------------------------------------------------- | ------------------------------------------------ |
| All Spiders Allowed to Access Any Static Resources    | A production instance you want crawled           |
| All Spiders Disallowed to Access Any Static Resources | Development and staging, blocks crawling         |
| Custom robots.txt Definition                          | Your own rules, the option Salesforce recommends |

Salesforce stores robots.txt as a site preference and replicates it between instances. The usual flow is to create it on staging and replicate site preferences to production. A robots.txt uploaded to a cartridge is replicated with code replication instead.

Storefronts built on the Storefront Reference Architecture (SFRA) serve their scripts, styles and images under `/on/demandware.static/`. A robots.txt rule for that path keeps crawlers from loading them.

The check reads the robots.txt the scan already fetched. It does not fetch anything new.

## Why it matters for AI agents

A robots.txt that disallows the whole site keeps Google and Bing from crawling your product pages. Their indexes feed many AI answers, so a blocked storefront is rarely found or cited there.

Blocking only the static path is quieter but still costly. Google says that blocking resources a page needs can make the page harder for it to understand. On an SFRA storefront those resources are the scripts, styles and images under `/on/demandware.static/`.

The staging preset is easy to carry over by accident. A routine replication of site preferences from staging can bring it back after you fixed it on production.

## How the scanner decides

The check runs only when the scan recognised Salesforce Commerce Cloud (see [platform detection](/knowledge-base/ecommerce-platform-detection)). On other platforms it is skipped and left out of the report. It makes no extra request.

Rules are evaluated per crawler, with the most specific matching rule winning and `Allow` winning a tie. A crawler without its own group follows the `User-agent: *` group.

- **Fail:** robots.txt disallows `/` for both Googlebot and Bingbot. This is what the "All Spiders Disallowed to Access Any Static Resources" preset produces.
- **Fail:** robots.txt disallows `/on/demandware.static/` for Googlebot or Bingbot. The message names the crawlers affected.
- **Pass:** neither of the above. A site without a robots.txt passes too, because nothing is blocked.

The evidence records whether the whole site is blocked, the static path tested and the crawlers it is blocked for.

The weight is 1, which means nice to have. It is not a gate for any level. A pass only says robots.txt lets search crawlers in. It does not say the pages are indexed or that an agent can buy.

## How to fix it

Set the production value explicitly, and make sure the next replication does not overwrite it.

### Salesforce B2C Commerce

1. In Business Manager, open the App Launcher and go to Merchant Tools, your site, SEO, Robots.
2. Choose "Define robots.txt Specific to Instance Type" and select the production instance.
3. Select "All Spiders Allowed to Access Any Static Resources", or "Custom robots.txt Definition" with rules that block only cart, checkout, account and search-result URLs and leave product pages and `/on/demandware.static/` open.
4. Keep "All Spiders Disallowed to Access Any Static Resources" for development and staging only.
5. If production gets robots.txt by replicating site preferences from staging, set the production value before the next replication, so the staging rules do not come back.
6. If a cartridge ships its own robots.txt, change it in the cartridge and replicate the code.

A custom robots.txt that keeps the static files open can look like this:

```robots
User-agent: *
Disallow: /cart
Disallow: /checkout
Disallow: /account
Disallow: /search
Allow: /on/demandware.static/
```

Adjust the paths to the URLs your storefront actually uses.

## Verify it yourself

Look at the live robots.txt on your storefront domain:

```bash
curl -s https://example.com/robots.txt
curl -s https://example.com/robots.txt | grep -inE '^disallow:\s*/\s*$|demandware\.static'
```

The second command prints any `Disallow: /` line and any rule that mentions the static path. No `Disallow: /` under `User-agent: *`, Googlebot or Bingbot, and no disallow rule for `/on/demandware.static/`, is what you want. To see which static files your pages load, list them from the home page:

```bash
curl -s https://example.com/ | grep -o '/on/demandware.static/[^"]*' | head -3
```

Rescan after the next replication to make sure the fix held.

## Common mistakes

- **Fixing production, then replicating from staging.** robots.txt is a site preference, so a replication can restore the staging preset. Set the production value per instance type.
- **Editing the wrong place.** A robots.txt in a cartridge travels with code replication, not with site preferences. Change it where it is defined.
- **Blocking the static path to save crawl budget.** Crawlers need the scripts, styles and images to understand the page.
- **Testing on the staging host.** The staging instance should block crawlers. Check the production domain.

## FAQ

### Where is robots.txt set in Salesforce Commerce Cloud?

In Business Manager under App Launcher, Merchant Tools, your site, SEO, Robots. Choose "Define robots.txt Specific to Instance Type" to give production and staging different values.

### Why did my production robots.txt change back to Disallow?

robots.txt is a site preference, and Salesforce replicates site preferences from staging to production. If staging uses the disallow preset and production has no value of its own, the next replication brings the block back.

### Should robots.txt block /on/demandware.static/?

No. SFRA storefronts serve their scripts, styles and images there, and Google says blocking resources a page needs can make it harder to understand.

### Does this check look at UCP or other agent files?

No. It is only about robots.txt. Salesforce publishes its Universal Commerce Protocol (UCP) profile on its commercecloud API host, not on the store domain, so a missing `/.well-known/ucp` on a Salesforce store domain is expected.
