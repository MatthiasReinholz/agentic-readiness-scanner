## In short

A product sold in several sizes or colours is really a group of items, each with its own SKU, price and stock. If the markup describes only the parent, an agent cannot tell which variant is available or what it costs. This check looks at variable products and expects them to be exposed as a schema.org ProductGroup with variants, as linked variant pages, or through the WooCommerce Store API.

## What this check looks at

schema.org models variants with three pieces:

- **`ProductGroup`**: the parent. It carries the shared `name`, a `productGroupID` that identifies the group, and `variesBy`, the properties that differ, such as `https://schema.org/size`.
- **`hasVariant`**: a list on the group with one `Product` per variant. Each variant has its own `sku` or `gtin`, its attribute values and its own `Offer`.
- **`isVariantOf`**: the reverse link. When each variant has its own URL, the variant page's Product names its group with `isVariantOf`.

Google's product variant documentation describes both forms: a single page that lists all variants under `hasVariant`, and separate pages per variant linked with `isVariantOf`.

## Why it matters for AI agents

An agent asked for "the blue mug in 350 ml" has to resolve a variant, not a product. With a ProductGroup, it can read that the blue 350 ml variant has SKU `MUG-350-BLU`, costs 24 euros and is in stock. With only a parent Product and a price range, it can only say that some variant exists somewhere in that range.

Variant identifiers matter just as much. If two variants share a SKU, or have none, an agent cannot refer to one of them unambiguously, for example when adding it to a cart. Google's variant guidelines say each variant must have a unique ID, such as a `sku` or `gtin`, for the same reason.

This check has weight 2, expected. It gates no level, but it decides whether agents can act on your variable products precisely.

## How the scanner decides

First the scanner decides whether a sampled product is variable. Any one of these signals counts:

- a WooCommerce variations form on the page,
- the Store API reports the product as type `variable`,
- the JSON-LD has a ProductGroup with `hasVariant`,
- the JSON-LD has a Product whose `isVariantOf` names a ProductGroup.

A variable product counts as modeled when its page has a ProductGroup with at least one variant under `hasVariant`, a Product with `isVariantOf`, or when the WooCommerce Store API lists its variations.

- **Pass:** every variable product sampled is modeled and no issue is found.
- **Warn:** some variable products are modeled and others are not. A full pass is also demoted to a warning when the variants under `hasVariant` lack a unique `sku` or `gtin` among them, or when the ProductGroup lacks `name` or `productGroupID`.
- **Fail:** no variable product sampled is modeled.
- **Skip:** no sampled product appears variable.

The evidence lists the signals found on each page, the number of JSON-LD variants and Store API variations, and the issues by page.

## How to fix it

Generate the group and its variants from your catalog data, so a new size or colour appears in the markup without manual edits.

### WordPress and WooCommerce

- WooCommerce core describes a variable product as a single Product, with an AggregateOffer when variation prices differ. It does not output a ProductGroup.
- The Store API still lists the variations, so the scanner counts the product as modeled. Agents that read only HTML do not see the variants, though.
- To expose them in markup, use an SEO plugin that outputs ProductGroup for variable products, or filter the core markup through `woocommerce_structured_data_product` and build `hasVariant` from the product's variations.
- Give every variation its own SKU under Product data, Variations. Empty or inherited SKUs produce variants without a unique identifier.

### Shopify

- Shopify themes that use the native product markup output a ProductGroup with one Product per variant, each with its own Offer.
- Check that each variant has a unique SKU or barcode in the product admin. Variants that share a SKU trigger the uniqueness warning.
- Custom themes that output only the first variant's price should switch to the native markup.

### Any other stack

- Choose one form per product. List all variants under `hasVariant` on one page, or give each variant its own URL and link it back with `isVariantOf`.
- Set `productGroupID` to the parent's stable identifier, such as the parent SKU.
- Give each variant `sku`, a GTIN where you have one, the attribute values named in `variesBy`, and its own `offers`.

When each variant has its own URL, the variant page can link to the group like this:

```json
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Stoneware Mug, 350 ml, Blue",
  "sku": "MUG-350-BLU",
  "color": "Blue",
  "size": "350 ml",
  "isVariantOf": {
    "@type": "ProductGroup",
    "name": "Stoneware Mug",
    "productGroupID": "MUG-350",
    "variesBy": ["https://schema.org/color", "https://schema.org/size"]
  },
  "offers": {
    "@type": "Offer",
    "price": "24.00",
    "priceCurrency": "EUR",
    "availability": "https://schema.org/InStock"
  }
}
```

## Verify it yourself

Google's [Rich Results Test](https://search.google.com/test/rich-results) recognises ProductGroup markup and reports variant problems under the product and merchant listing results. The [Schema Markup Validator](https://validator.schema.org/) shows the full tree, so you can check that each variant has its own SKU and Offer.

To check whether WooCommerce lists the variations of a product:

```bash
curl -s "https://example.com/wp-json/wc/store/v1/products?search=stoneware%20mug" | jq '.[0] | {type, variations: (.variations | length)}'
```

## Common mistakes

- **One Product with a price range.** The markup says the mug costs 19 to 29 euros but not which variant costs what.
- **Variants without their own SKU.** Every variant inherits the parent's SKU, so none can be told apart.
- **A ProductGroup with no productGroupID.** Google's variant documentation says the group needs its own unique ID, and `productGroupID` is where it goes.
- **Variant offers on the group only.** The group carries one Offer, and the variants carry none.
- **Mixing both forms on one page.** Listing variants under `hasVariant` and also marking the page's Product as a variant of another group confuses readers.

## FAQ

### What is the difference between ProductGroup and Product in schema.org?

A ProductGroup is the parent of a set of variants that share a design but differ in properties such as size or colour. Each variant is a Product. Shoppers buy Products. The group exists to tie them together.

### Do I need a separate URL for each variant?

No. Google's documentation supports both a single page that lists every variant and one page per variant. Choose the one that matches how your store already works.

### What should productGroupID be?

A stable identifier for the parent product, such as the parent SKU or an internal model number. It should not change when variants are added or removed.

### My WooCommerce store passes, but the markup has no ProductGroup. Why?

The Store API lists the variations, and the scanner accepts that as a way to expose them. Agents that read only the page markup still see a single Product, so adding ProductGroup markup is worthwhile.
