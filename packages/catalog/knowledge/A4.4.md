## In short

A server card that points at a dead or wrong URL is worse than no card. This check sends a read-only JSON-RPC request to the MCP (Model Context Protocol) endpoint named in your server card and confirms that the answer comes from an MCP server. It runs only when the [MCP server discovery check](/knowledge-base/mcp-server-discovery) found an endpoint, and it carries weight 1, nice to have.

## What this check looks at

MCP lets an AI agent call tools on a server. It uses JSON-RPC 2.0 messages, a simple format for remote calls: each request names a method, and the answer carries a result or an error. Over the web, they travel on the Streamable HTTP transport: the client sends each message as an HTTP POST to a single endpoint URL. The server answers with a JSON body or with server-sent events, a stream of messages over one HTTP response.

The 2026-07-28 revision of the specification adds a mandatory, read-only method called `server/discover`. A client can call it to learn the server's name, version and supported protocol versions. It changes nothing on the server, which makes it a safe probe.

The scanner sends this request:

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{...}}}
```

The `_meta` object carries the protocol version and the scanner's client name, as the revision prescribes.

Servers on the 2025 revisions keep a session, and some refuse every method before the client opens one with an `initialize` handshake. They answer `server/discover` with a plain HTTP 400. In that case the scanner sends the 2025-06-18 `initialize` request once, as every client does. These two are the only requests the scanner ever sends with a body. Neither creates or changes anything beyond the session the handshake opens.

## Why it matters for AI agents

An agent that follows a card to an endpoint needs a working MCP server at the other end. If the URL returns a 404 page, a 405 or the shop's home page, the agent gives up. It has no way to tell a typo from a removed service.

Older servers do not know `server/discover`. That is not a problem. The 2026-07-28 transport tells such a server to answer 404 with a JSON-RPC "method not found" error (code -32601). That answer still proves an MCP server is listening, so the check accepts it. A server that insists on the 2025 handshake proves the same by answering `initialize`.

Passing proves reachability and the transport. It does not prove which tools the server offers or that they work.

## How the scanner decides

The check is skipped when no endpoint was discovered. Otherwise the scanner sends the POST above to the endpoint from the server card.

- **Pass:** the body is a JSON-RPC message, whatever the HTTP status. That covers a `server/discover` result, a 404 with error -32601 from an older server, and a 400 with error -32020 when the server rejects a header. A response with the `text/event-stream` content type also passes. So does a 401 with a `WWW-Authenticate` header, which means the server requires authorization.
- **Pass:** `server/discover` got a plain HTTP 400, and the `initialize` handshake that follows gets a JSON-RPC answer.
- **Fail:** a 404 or any other answer without a JSON-RPC body, such as a 401 without `WWW-Authenticate`, a 405 (the URL does not accept POST), a 500 or an HTML page.
- **Skipped:** the request got no response, was rate limited (429) or hit a gateway error (502, 503, 504). These say nothing about the server.

The evidence records the status, the content type, whether the body was JSON-RPC and whether a `WWW-Authenticate` header was present.

## How to fix it

Start from the failure message. It tells you whether the URL is wrong, the method is wrong or the server is down.

### WordPress and WooCommerce

- Check the endpoint URL in the plugin that runs your MCP server and compare it with the card. Permalink changes and trailing slashes are common causes of a mismatch.
- Security plugins and some hosts block POST requests with a JSON body to unknown routes. Allow the MCP route explicitly.
- Exclude the endpoint from page caching. A cached HTML page served for a POST request fails the check.

### Shopify

- Shopify's own MCP endpoint at `/api/ucp/mcp` is checked by the [agentic storefront check](/knowledge-base/shopify-agentic-storefront), not here. This check only applies if you publish a server card for another MCP server.

### Any other stack

- Point the card at the Streamable HTTP endpoint itself. A documentation page or the server's root path does not count.
- Make sure the endpoint accepts POST with `application/json` and answers with JSON-RPC, even for methods it does not implement.
- If the server requires a login, return 401 with a `WWW-Authenticate` header instead of redirecting to a sign-in page. The [OAuth discovery check](/knowledge-base/oauth-discovery-for-mcp) covers the metadata that should come with it.
- Keep a reverse proxy or CDN from turning JSON-RPC errors into HTML error pages.

## Verify it yourself

Send the same request yourself:

```bash
curl -si -X POST https://example.com/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: server/discover" \
  -d '{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{}}'
```

Look for a body that starts with `{"jsonrpc":"2.0"`, or a `data:` line that carries one. An HTML page or an empty 404 means the card points at the wrong place. The MCP Inspector, the protocol's open-source debugging tool, is another way to connect and list the tools.

## Common mistakes

- **Pointing the card at `/.well-known/` or a docs page.** The endpoint must be the URL that accepts JSON-RPC POSTs.
- **A server that answers only GET.** The Streamable HTTP transport sends messages by POST. A 405 fails the check.
- **Login redirects.** A 302 to a sign-in page ends in HTML, which no agent can use. Answer 401 instead.
- **An HTML error page from the proxy.** The server may be fine, but if a gateway rewrites its 404 into a branded page, agents cannot read the JSON-RPC error.

## FAQ

### What is server/discover in MCP?

It is a read-only JSON-RPC method that the 2026-07-28 revision makes mandatory. It returns the server's identity and supported protocol versions.

### My MCP server is older and does not support server/discover. Does it fail?

No, if it follows the transport. A server that answers 404 with a JSON-RPC -32601 "method not found" error passes, because the answer proves the transport works. So does a 2025 server that refuses `server/discover` with a plain 400 and then answers the `initialize` handshake.

### Does the scanner call my tools or change any data?

No. It sends a `server/discover` request, which only reads the server's description. Only when a 2025 server refuses that with a plain 400 does it send one `initialize` handshake, which opens a session and nothing more. It never lists or calls tools.

### Why does a 401 count as reachable?

A 401 with a `WWW-Authenticate` header is how an MCP server that requires authorization is supposed to answer an anonymous client. It shows the server is there and expects a token.
