## In short

An Ecwid store embedded in a custom website builds product links like `/store/#!/product-name/p/123456` unless clean URLs are switched on. Everything after the `#` stays in the browser and never reaches the server, so a crawler or agent cannot fetch one product page on its own. This check warns when store links use that form, or when a custom site's integration code does not switch clean URLs on.

## What this check looks at

Ecwid explains where clean URLs come for free. On Instant Site, Ecwid's own website builder, and on WordPress or Wix through Ecwid's plugins, SEO-friendly URLs are automatic. On a custom-made website they must be enabled by hand, with integration code and server configuration.

Ecwid's guide for custom websites shows the change:

| Clean URLs | Example product URL                                  |
| ---------- | ---------------------------------------------------- |
| Off        | `https://example.com/store/#!/product-name/p/123456` |
| On         | `https://example.com/store/product-name`             |

Clean URLs remove the hashbang (`#!`) and, with a second setting, the numeric ID (`/p/123456`).

The check reads the home page the scan already fetched:

- the links on the page, looking for `#!/`
- the generator meta tag, page code and response headers that show Instant Site, WordPress or Wix
- the page code, looking for `cleanUrls` set to true

## Why it matters for AI agents

The part of a URL after `#` is a fragment. The URL standard, RFC 3986, says fragments are not sent to the server. So `/store/#!/shoes/p/1` and `/store/#!/hats/p/2` are one request for `/store/` as far as the server is concerned. A crawler that does not run the store's script sees one page, not a catalog.

With clean URLs each product has an address the server answers. Agents can open it directly, cite it and put it in a sitemap.

On Instant Site and on WordPress and Wix, Ecwid also creates a static HTML copy of every product and category page for search engines. Structured data is JSON-LD plus Microdata on Instant Site and WordPress, and Microdata only elsewhere.

## How the scanner decides

This check runs only on sites with an Ecwid store, when the scan recognised it (see [platform detection](/knowledge-base/ecommerce-platform-detection)). On other platforms it does not run and reports leave it out. It reads only the home page and makes no extra request.

The steps run in this order:

1. **Warn:** any link on the home page contains `#!/`. The message quotes the first one. This applies on every host, Instant Site, WordPress and Wix included.
2. **Pass:** the page is an Instant Site (generator `ec-instant-site`), a WordPress site (generator or a `/wp-content/` path in the page) or a Wix site (generator or an `x-wix-request-id` header). Ecwid documents clean URLs as automatic there.
3. **Pass:** the page's code sets `cleanUrls` to true, for example `window.ec.config.storefrontUrls.cleanUrls = true`.
4. **Warn:** otherwise. The store sits in a custom site without clean URLs switched on, so its product pages default to hashbang URLs.

The evidence records the detected host, whether clean URLs are configured and up to five hashbang links. The weight is 1, which means nice to have. It gates no level. A pass says the store's URLs can be fetched. It does not test the rewrite rules on your server or say that an agent can buy.

## How to fix it

Use the mechanism Ecwid provides for your setup.

### Ecwid on a custom website

1. Follow Ecwid's guide "Enable clean store URLs on a custom website".
2. Add a script that runs before the Ecwid script and sets `cleanUrls` and `slugsWithoutIds` to true, as shown below.
3. Add the server rewrite rules the guide gives for your web server, so every URL under the store page returns that page.
4. Open a product URL directly in a private window. It must load the product, not a 404 or the store's start page.
5. Update your sitemap and internal links to the clean URLs.

```html
<script>
  window.ec = window.ec || {};
  window.ec.config = window.ec.config || {};
  window.ec.config.storefrontUrls = window.ec.config.storefrontUrls || {};
  window.ec.config.storefrontUrls.cleanUrls = true;
  window.ec.config.storefrontUrls.slugsWithoutIds = true;
</script>
```

### Ecwid Instant Site, WordPress and Wix

Clean URLs are automatic on these hosts. If the scan still finds `#!/` links, they are usually hard-coded in menus, banners or content. Replace them with the clean URLs from the store. On WordPress and Wix, use Ecwid's own plugin for the platform rather than pasting the embed code, since the plugin is what provides clean URLs and static page copies.

## Verify it yourself

Look for hashbang links and for the clean URL setting on your home page:

```bash
curl -s https://example.com/ | grep -oE 'href="[^"]*#!/[^"]*"' | head
curl -s https://example.com/ | grep -io 'cleanurls[^;,]*'
```

No output from the first command is what you want. The second should show `cleanUrls` set to true on a custom site. Then fetch a product URL directly:

```bash
curl -sI https://example.com/store/product-name
```

An HTTP 200 means the server answers the clean URL. Rescan to confirm.

## Common mistakes

- **Setting the option after the Ecwid script.** The configuration must run before the Ecwid script loads.
- **Skipping the server rewrite rules.** Without them, clean product URLs return a 404 when opened directly.
- **Leaving hard-coded hashbang links.** Menus, banners and blog posts written with `#!/` links keep the old form.
- **Embedding the widget code on WordPress or Wix.** Ecwid's plugin, not the raw embed, is what gives clean URLs and static copies there.

## FAQ

### Why do Ecwid product URLs contain #!?

On a custom website, Ecwid builds store links with a hashbang unless clean URLs are switched on. The store's script reads the part after `#!` in the browser to decide which product to show.

### Can search engines and agents read hashbang URLs?

The part after `#` never reaches the server, under RFC 3986. A crawler or agent that does not run the store's script gets the same store page for every product link.

### Do I need to do anything on Instant Site, WordPress or Wix?

Not for the URLs. Ecwid documents clean URLs as automatic there. Only remove any hard-coded `#!/` links in your own menus or content.

### Why does the scanner only warn instead of fail?

A browser running the store's script can still show every product. Clean URLs make each product fetchable on its own, which is an improvement for crawlers and agents, so the check warns and is weighted as nice to have.
